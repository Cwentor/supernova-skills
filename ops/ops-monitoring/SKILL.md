# 线上监控与可观测性

## Overview

可观测性由三根支柱构成：**日志**（离散事件，回答「当时到底发生了什么」）、**指标**（可聚合数值，回答「是否异常、趋势往哪走」）、**追踪**（跨服务调用链，回答「慢在哪一跳、断在哪个环节」）。三者互补、不能互替：只有指标能知道错误率涨了，却不知道原因；只有日志能知道报了什么错，却撑不起长期聚合与跨实例对比。

核心原则：**每一条指标、日志、告警都必须能回答一个具体的排障问题；回答不了的就是噪音，噪音会稀释真正有用的信号。**

默认姿态是**能力探测**，不假设任何平台：环境中已有指标 / 日志 / 追踪类工具，就接进去、用它已有能力，不自建重复轮子；没有，则用通用替代——**结构化日志写到文件 + 一个定时检查脚本**（轮询关键端点与关键字，异常时走已有通道通知到人）。先有可用的最小闭环，再谈平台。

## 何时使用

症状（命中任意一条即可用）：

- 线上出问题只能靠用户投诉、客服转达才知道，自己人比用户晚发现。
- 加了一堆指标和面板，没人看得懂、也没人看。
- 告警天天响、响完没人处理，真出事那次反而被淹没。
- 故障复盘找不到证据：不知道当时跑的哪个版本、哪台实例、哪条链路出问题。
- 要上线新服务，却说不清「怎么判断它是健康的」。
- 日志量涨到成本扛不住；或者反过来，出问题时日志里查不到关键上下文。

何时不用：

- 本地跑的一次性小脚本、交互式数据分析、临时的调试程序——打印到终端即可。
- 一次性任务、用完即弃的迁移脚本——没有第二次运行，也就没有长期观测价值。
- 纯研究性原型，还没决定要不要长期维护。

不确定当前该用哪条技能线时，先走 `meta-skill-router` 定路由；本技能只负责「上线后怎么知道它好不好」。

## 日志

- **结构化优于纯文本**：以键值 / JSON 形式输出，字段固定（时间、级别、服务、环境、事件名、关联 ID、关键业务维度）。纯文本只有在给人眼读时才合格。
- **级别怎么定**：ERROR 表示需要人介入或已经影响用户；WARN 表示可自愈但值得观察；INFO 记录状态变迁与关键业务事件；DEBUG 只用于临时排查，默认关闭。**把「预期内的失败」记成 ERROR 是告警疲劳的头号来源。**
- **关联 ID / 请求追踪**：每个请求进来时生成或透传一个关联 ID，贯穿所有下游调用并出现在每条日志里。没有它，日志就是一盘散沙；有它，一次查询就能拼出完整时间线。
- **敏感信息脱敏**：口令、令牌、身份证件、完整卡号、个人联系方式一律不进日志。脱敏在写入前做，不是事后检索时过滤——日志一旦落盘，就已经泄露了。
- **采样与成本**：高频成功路径可以采样，**错误路径一律不采样**。设定日志体积上限与保留期限，超限时优先降 DEBUG 与高频 INFO，而不是关掉 ERROR。
- **日志里最该有的上下文**：版本号、环境、实例标识、关联 ID、上下游服务名、耗时、结果状态、可归类的事件名。缺了「版本」和「关联 ID」的日志，在故障现场基本用不上。

## 指标

三种互补的观察角度，按对象选：

- **四个黄金信号**（面向用户感受的服务视角）：延迟、流量、错误、饱和度。
- **RED 方法**（面向请求型服务）：Rate 请求速率、Errors 错误数、Duration 耗时分布。
- **USE 方法**（面向资源）：Utilization 使用率、Saturation 饱和度、Errors 错误数。

其余纪律：

- **命名与标签**：命名带单位与语义（如 `http_request_duration_seconds`），避免含义模糊的缩写。
- **标签基数爆炸**是最高频的自伤方式：**绝不把用户 ID、邮箱、订单号、完整 URL、异常堆栈放进标签**。基数高的维度放日志或追踪，不放指标。
- **类型选择的直觉**：只增不减的累计量用计数器；可上可下的瞬时值（队列长度、连接数）用仪表；耗时与大小分布用直方图 / 摘要，并在定义时就选定分位口径，不要事后拼凑。

环境里没有指标库时，别急着搭建：先用定时脚本采集少量关键数字（成功率、耗时、队列深度）写入一份带时间戳的记录，用它能回答的问题决定是否值得上完整方案。

## 健康检查

三种探针语义不同，混用会造成事故：

- **liveness**：进程是否还活着、是否需要被重启。**只反映本进程自身**。
- **readiness**：此刻能否接流量。依赖不可用时应为「不就绪」，但**不触发重启**。
- **startup**：启动是否完成，用于给慢启动服务更宽的起跑窗口。

常见误用与修法：

- **把下游依赖（数据库、缓存、第三方接口）挂进 liveness** → 下游抖动导致全部实例被判死并级联重启，把局部故障放大成全站故障。依赖检查放 readiness，或单独做降级标记。
- **liveness 里做重活**（查库、跑聚合）→ 探针本身成了新的故障源。liveness 应廉价、无副作用、只查本进程。
- **就绪与存活共用一个端点** → 无法表达「活着但暂时不该收流量」。至少分成两个端点。
- **探针超时与阈值拍脑袋** → 阈值必须比正常响应时间高一个数量级，否则会出现「一切正常而实例被反复重启」。

## 追踪

- **什么时候值得上**：跨三个以上服务、或一次请求会经过异步队列 / 后台任务、或排查「整体慢但每个服务指标都正常」这类问题时，追踪的收益最大。
- **采样策略**：常规流量用较低比例的头部采样控制成本；**错误请求与高延迟请求强制全采**。采样率必须写进文档，否则会把「采样后的数据」当成「全量事实」得出错误结论。
- 若环境没有追踪设施，可用结构化日志里的关联 ID 与耗时字段手工拼出调用链，代价是没有自动传播，需要每层显式传递。

## 告警

- **可行动才告警**：每条告警都要能回答「收到它的人现在应该做什么」。答不出动作的，改成仪表盘。
- **分级与路由**：分「立刻叫人（影响用户、需人工干预）」「工作时间处理（容量趋势、非用户路径失败）」「仅记录（信息性）」三档，分别路由到不同通道。所有告警都走同一个最吵的通道，等于没有分级。
- **每个告警配 runbook 链接**：一句话说明含义、常见原因、第一反应动作、升级路径。没有 runbook 的告警是在把排障成本转嫁给凌晨被叫醒的人。
- **告警疲劳的代价与治理**：频繁误报让人形成「先忽略」的习惯，真故障因此被漏掉。治理动作是定期的：统计告警量与处理率，删掉长期无人处理或反复误报的规则，收紧阈值。
- **什么该做成仪表盘而不是告警**：缓慢趋势（磁盘逐月增长）、没有明确动作的异常波动、需要人工判断的多因素组合——这些放面板供人排查时看，不放告警。

## SLO 与错误预算

- **怎么定**：选一个用户真正在意的行为（如「登录成功且 1 秒内返回」），给出目标（如 99.9%）与统计窗口。**SLO 描述用户感受，不是内部技术指标的副本。**
- **错误预算是用来做决策的**：预算充足时可以承受更高发布频率、更大胆的变更；预算持续被烧光时，暂停功能发布、优先修复稳定性。没有这个决策用途，SLO 只是墙上的一张纸。
- 起步阶段若定不出正式 SLO，先记录实际达成水平，观察几周再定目标——凭空拍一个够不到的目标，只会催生造假数据。

## 仪表盘

按排障路径分层，而不是按数据来源堆图：

1. **总览层**：核心用户的成功率与延迟、错误预算剩余。给值班人第一眼判断「是不是真出事」。
2. **服务层**：按服务拆的 RED 曲线，用于定位是哪个服务。
3. **实例层 / 依赖层**：具体实例、依赖出口、队列深度，用于定位具体原因。

每条曲线都要有结论指向：图要能回答问题，而不是好看。面板上写清单位、时间窗口、正常范围带。**没有结论的图墙是负资产**——它占用了故障时最宝贵的注意力。

## 与其他技能的分工

- `meta-skill-router`：不确定该走哪条技能线时，由它定路由。
- `ops-deploy`：发布流程、回滚门禁；健康检查与探针阈值是部署配置的一部分，改动需与发布节奏对齐。
- `dev-debugging`：告警触发后的调查流程，本技能负责「把证据留下」，它负责「用证据定位」。
- `dev-verification`：声称「监控已生效 / 告警已配好」之前，必须按它给出证据（造一次可控故障，确认信号与告警真的到达）。
- `dev-code-conduct`：写插桩、日志与探针代码时的行为准则底座。
- `ops-wizard`：需要在第三方控制台里由人手工点操作（建通知通道、开权限、绑账号）时，用它生成交互式向导，而不是让 agent 猜测界面。
- `lang-clickhouse-patterns`：当日志或指标要落到列式库做聚合分析、需要设计表结构与优化查询时使用。

## 常见错误

| 出错点 | 修法 |
| --- | --- |
| 日志全是自由文本，故障时无法按字段检索 | 改成结构化键值输出，固定字段集，先固定事件名与关联 ID |
| 所有异常都记 ERROR，包括预期内的失败 | 重新分级：影响用户或需人介入才 ERROR，可自愈的降 WARN |
| 指标标签里塞用户 ID / 订单号 / 完整 URL | 把高基数维度移出指标，放日志或追踪 |
| 用仪表记录只增不减的累计量（或反之） | 累计量用计数器，瞬时量用仪表，分布用直方图 |
| 把数据库依赖写进 liveness 探针 | 依赖检查挪到 readiness；liveness 只查本进程 |
| 告警阈值拍脑袋，正常波动就报 | 用历史数据定阈值并留出正常范围带，告警必须可行动 |
| 告警没有 runbook，值班人不知道做什么 | 每条告警补一句含义 + 第一反应动作 + 升级路径 |
| 堆了一墙好看的图，故障时看不出结论 | 按总览→服务→实例分层重排，删掉没有结论的图 |
| 只做监控不做验证，上线后才发现信号没到 | 发布后主动制造一次可控失败，确认信号与告警链路通畅 |

## 借口 vs 现实

| 借口 | 现实 |
| --- | --- |
| 「先把功能发了，监控以后补」 | 「以后」通常指故障之后。最小的健康检查与错误日志是上线门槛，不是后续优化项。 |
| 「告警多响几次总比漏掉好」 | 频繁误报训练出「先忽略」的习惯，真故障正是被这样漏掉的。误报和漏报一样是缺陷。 |
| 「日志打全量最保险」 | 全量日志带来成本、噪音与凭据泄露风险。该问的是「排障时需要哪几个字段」，不是「能不能都留下」。 |
| 「指标加上去就一定会有人看」 | 没有人认领、没有结论指向的指标不会有人看，只会占资源。每条指标都要有明确的排障用途。 |
| 「健康检查就返回 200 吧」 | 恒真探针等于没有探针，调度器无法区分「服务可用」与「进程还在」。 |
| 「SLO 是给大公司用的」 | SLO 是排序工具。定不出正式目标时，先用实测达成水平当基线，也比没有强。 |
| 「这次故障太特殊，复盘没必要」 | 复盘的价值不在归因给谁，而在补上缺失的证据与告警。特殊故障往往是同一类缺口的表现。 |

## 红线自查

逐条核对，任一条命中则不得宣称完成：

- [ ] 每条指标、日志、告警都能说出一句它要回答的排障问题。
- [ ] 每个请求有关联 ID，并贯穿下游调用。
- [ ] 日志中没有口令、令牌、证件号、完整卡号等敏感信息。
- [ ] 指标标签不含用户 ID、订单号、完整 URL 等高基数取值。
- [ ] liveness 只检查本进程，不依赖任何外部下游。
- [ ] 每条告警都能回答「收到后现在做什么」，且有 runbook 链接。
- [ ] 告警已分级并路由到不同通道，不是全部挤在一个最吵的通道里。
- [ ] 仪表盘按总览→服务→实例分层，每张图都有结论指向。
- [ ] 已按 `dev-verification` 制造一次可控故障，确认信号与告警真实到达。
