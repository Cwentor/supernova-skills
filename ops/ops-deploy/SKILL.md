# 部署与上线

## Overview

这个技能只管一件事：**把变更安全地送进生产，并且能安全地退回来**。范围是部署策略选择、Dockerfile 与镜像、数据库迁移的先后顺序、部署前的验证闭环、回滚预案。

四条核心原则：

1. **可回滚**——没有回滚方案的发布不算发布。发之前先回答：怎么退，退回去要多久。
2. **可验证**——部署命令返回成功 ≠ 上线成功；健康检查、冒烟、错误率说了算，且验证方式必须在部署前就定好。
3. **幂等**——同一份产物重复部署结果一致：镜像用固定 tag 或 digest，迁移可重复执行（`IF NOT EXISTS`、只处理 `IS NULL` 的行），脚本重跑安全。
4. **顺序**——迁移与代码不一起上，而是分先后：先向后兼容地扩（expand），再发新代码，再回填，最后收（contract）。谁先谁后搞反 = 停机。

分工：证据纪律与「完成」的判定归 dev-verification；分支怎么落地、PR 怎么开归 dev-finish-branch；`reset --hard`、`push -f` 这类破坏性操作的止损归 dev-git-guardrails；写部署代码时的行为准则归 dev-code-conduct。

## 何时使用

触发场景：

- 要发一次版本：`kubectl apply`、`docker compose up -d`、平台 CLI、CI 的 deploy job
- 要写或改 Dockerfile、compose 文件、镜像构建流程
- 要改表结构：加列、加索引、删列、改类型、做数据回填
- 要选部署策略，或要写发布前检查清单与回滚预案
- 事故现场要立刻回滚，需要判断「退得动吗」

不适用：

- 纯本地脚本或库，没有部署目标、没有数据库
- 只是问「CI 为什么红」——那是修 CI，不是部署设计
- 完整的可观测性体系设计（本技能只写「上线后头 30 分钟看什么」）

## 部署策略选择

| 策略 | 做法 | 适用 | 代价 | 回滚 |
|------|------|------|------|------|
| 滚动发布 rolling | 逐个替换实例 | 默认选择；变更是向后兼容的 | 新旧版本同时在线，schema 与接口必须兼容 | 慢：反向再滚一遍 |
| 蓝绿 blue-green | 两套等同环境，验证后原子切流量 | 关键服务、对问题零容忍、付得起双倍资源 | 部署期间 2 倍基础设施 | 最快：切回旧环境 |
| 金丝雀 canary | 小比例真实流量先试，指标正常再放量 | 高流量服务、高风险变更、有流量切分与指标对比 | 需要流量切分设施和监控 | 快：权重归零 |

选型规则：要瞬时回滚且掏得起双倍资源 → 蓝绿；拿不准变更是否安全、但能观察指标 → 金丝雀；两者都不具备 → 滚动发布，代价是把「向后兼容」当成硬约束来管。

## 容器与镜像

- **多阶段构建**：deps → build → runtime 三段。runtime 只带产物与生产依赖，不带编译器、源码、测试。
- **层缓存顺序**：先 COPY 依赖清单（`package.json`、`go.mod`、`requirements.txt`）并安装，再 COPY 源码。反过来改一行代码就重装全部依赖。
- **锁版本**：`node:22-alpine`，不用 `:latest`。构建可复现，才谈得上回滚到「上一版」。
- **非 root**：建固定 uid（如 1001）用户并 `USER appuser`，COPY 时 `--chown`；编排里配 `security_opt: no-new-privileges:true`、`cap_drop: [ALL]`。
- **瘦身**：`.dockerignore` 排掉 `node_modules`、`.git`、`.env`、`dist`、`coverage`、`tests`；`npm ci --omit=dev` 或 `npm prune --omit=dev`，生产镜像不装 dev 依赖。
- **健康检查分三层**：`readinessProbe` 决定是否接流量，`livenessProbe` 决定是否重启，`startupProbe` 兜住慢启动。就绪探针不要指向会检查下游依赖的接口，否则数据库抖一下所有实例被同时踢出。给 `/health/detailed` 这类接口单独留内部路径。
- **配置外置**：配置走环境变量并在启动时校验（schema 校验），校验失败立刻退出（fail fast）；镜像和 compose 文件里不出现密钥，`.env` 进 `.gitignore`。
- **compose 的定位**：开发环境与单机小规模用它（绑定挂载热重载、`/app/node_modules` 匿名卷保护依赖、`depends_on: service_healthy`）；生产多容器负载交给编排平台，别用裸 compose 硬扛。

## 数据库迁移

**铁律：不准手改生产库，一切走迁移文件；已部署的迁移文件不可编辑，只能新增一个。**

expand-contract 三段：

```
EXPAND   加新列/新表（可空或带默认值），部署能同时写新旧两处的代码，回填历史数据
MIGRATE  部署改为从新结构读、同时继续写新旧两处，校验两边数据一致
CONTRACT 部署只读写新结构，最后用一次独立迁移删掉旧列/旧表
```

顺序敏感的操作：

| 想做的事 | 正确顺序 |
|----------|----------|
| 加列 | 先加可空列、或带默认值的列（PG 11+ 带默认值不重写表），再发代码 |
| 改列名 | 不要重命名：加新列 → 回填 → 双写 → 切读 → 删旧列，跨多个发布周期 |
| 删列 | 先删代码里的引用并发布 → 观察一个周期 → 再用独立迁移删列 |
| 加索引 | 大表上用 `CREATE INDEX CONCURRENTLY`（不能在事务块内运行），否则接受写入阻塞 |
| 加 NOT NULL | 先加列 → 回填 → 再加约束；绝不 `ADD COLUMN ... NOT NULL` 不带默认值 |

长事务与锁：

- 全表 `UPDATE` 会长时间持锁、撑爆 WAL。改成分批（`LIMIT` + `FOR UPDATE SKIP LOCKED`），打印进度，直到更新行数为 0。
- DDL 与 DML 拆成两个迁移，别混在一个事务里。
- 在生产规模的数据副本上试过再上：100 行上正常，不代表 1000 万行不锁表。

**迁移失败怎么退**：先分清「整个事务回滚了」还是「部分已生效」。schema 变更多半可以走回退迁移；数据回填通常**不可逆**——所以要靠回填脚本自身幂等（只处理需要处理的行）保证重跑安全，而不是指望回滚把数据变回去。

## 部署前验证闭环

**门禁：本地跑的那一套检查必须与 CI 一致。不一致的绿，等于没绿。**

1. 用一条命令跑完全部分级检查：有 CI/CD 平台就把同一组命令接进 pipeline；无平台则用本地等效做法——`make verify`、`scripts/verify.sh`，或 package.json 里的一个 script 串起来。
2. 检查项按序：构建 → 类型检查 → lint → 测试（带覆盖率）→ 依赖 CVE 与硬编码密钥扫描 → 迁移在生产副本上演练 → 镜像构建 + 健康检查冒烟。
3. 失败就地修，重跑，直到全绿。红着往下走、想着「部署时再修」，只是把故障搬到生产。
4. 留证据：命令、退出码、通过数、覆盖率数字。说不清哪个命令绿了的，就是没验证——判定纪律归 dev-verification。
5. 检查要针对**即将部署的那个产物**再跑一次：产物是新的，就在新产物上冒烟。

「我本地能跑」永远不算证据：容器里能跑、用生产配置能跑、连真实数据库能跑，才算。

## 发布检查清单与回滚预案

发布前逐条核对：

- [ ] 上一版镜像/产物仍可拉取，且引用的是不可变 tag 或 digest
- [ ] 迁移向后兼容，旧代码能跑在新 schema 上（滚动与蓝绿期间必须成立）
- [ ] 新功能有开关能关，不必重新部署
- [ ] 健康检查接口能区分「活着」与「就绪」，已在预发验证过
- [ ] 环境变量、资源限制、副本数已确认
- [ ] 回滚演练过：真的执行过回滚命令，知道恢复要多久
- [ ] 上线后 30 分钟有人盯错误率、延迟、日志

回滚预案必须回答四件事：**触发条件**（错误率 > X%、关键链路失败、数据写错）、**回滚命令与执行人**、**恢复耗时与期间的业务降级**、**迁移能不能退**。

最后一条最硬：数据迁移往往不可逆——**回滚也回不动迁移**。能退的是代码，退不掉的是已经写进库里的新格式数据。所以预案要建立在「旧代码能容忍新 schema」的兼容设计上，而不是假设连迁移一起退。

## 常见错误

| 症状 | 修法 |
|------|------|
| 用 `:latest`，回滚时不知道「上一版」是哪个 | 固定 tag 或 digest，发布记录里存下 digest |
| 镜像 1GB+、构建十几分钟 | 多阶段构建 + 先依赖后源码的 COPY 顺序 + `.dockerignore` |
| 容器以 root 跑，挂载卷权限错乱 | 建固定 uid 用户、`USER` 切过去、构建期 `--chown` |
| 就绪探针查数据库，DB 抖动时全实例下线 | 就绪探针只反映本进程状态，下游依赖放进详细健康检查 |
| 上线即报错：代码先于迁移上线 | 迁移先扩（向后兼容），代码后发；或让新代码容忍旧 schema |
| 删列后旧实例还在跑，报 column does not exist | 先删代码引用、发完、观察一个周期再删列 |
| 迁移在小库上秒过，生产锁表半小时 | 分批回填、并发建索引、在生产规模副本上演练 |
| 回滚后数据已被新代码写成新格式 | 用 expand-contract 的兼容窗口，别把不可逆数据变更绑进同一次发布 |
| 密钥写在 Dockerfile 或 compose 里 | 运行时注入环境变量或密钥管理器，并轮换已暴露的密钥 |

## 借口 vs 现实

| 借口 | 现实 |
|------|------|
| 「先发上去再说，出问题再修」 | 没有回滚方案就没有发布资格。先把回滚预案写完，再执行部署。 |
| 「迁移跟代码一起上没关系」 | 一起上就是新代码去读还不存在的列。expand-contract 存在的唯一理由就是避免这个。 |
| 「回滚不就是重新部署旧版本」 | 容器能回滚，数据不一定。不可逆迁移跑完后，旧代码必须能容忍新 schema。 |
| 「生产上手动改一下更快」 | 手改没有审计、不可复现、环境间漂移。写迁移文件，哪怕只有一行。 |
| 「本地测过了，CI 太慢就直接发」 | 本地那套和 CI 不一致时，绿的不是同一个东西。门禁没绿就不发。 |
| 「这是小表，不用管锁」 | 表会长大。今天的 100 行不是半年后的 1000 万行。 |
| 「就这一次，来不及」 | 一次生产事故的修复成本，永远高于多花二十分钟写回滚预案。 |

## 红线自查

- 发布前说不出回滚命令，或从没演练过
- 迁移与代码绑在同一次发布，且迁移含不可逆的数据变更
- 新列 `NOT NULL` 不带默认值，或大表上非并发建索引
- 直接改生产数据库，或编辑已部署的迁移文件
- 镜像用 `:latest`、以 root 运行、密钥烘进镜像
- 用本地那套检查替代 CI 门禁，或检查没绿就部署
- 未经预发（或等价的副本环境）验证就上生产
- 没有健康检查或就绪探针，只靠「进程还活着」

任何一条命中：停下来补齐，再发布。
