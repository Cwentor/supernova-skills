# meta-security-audit · 跨语言安全审查

语言无关的安全底座：在**写**敏感代码时就按攻击面过一遍，而不是等出事。任何语言、任何框架都适用。

## 定位与分工

- **本件**：跨语言的安全意图与自查清单——认证授权、输入验证、注入、机密、输出编码、限速、泄露、依赖。
- 框架级安全配置（过滤器链、方法级鉴权注解、密码编码器参数）→ 对应语言的 `lang-*-security`。
- 一段 diff 的整体质量评审（结构、可读性，顺带安全）→ `dev-review-code`。
- 上线前的部署顺序与回滚预案 → `ops-deploy`；本件只负责「上线前安全项是否清零」。

## 四条底层原则

1. **信任边界**：越过进程、网络、用户输入边界的任何数据都不可信，先验证再使用。
2. **最小权限**：能只读就不给写，能给单表就不给全库，能发短期令牌就不发长期。
3. **失败关闭**：鉴权、校验、限流的异常路径必须**拒绝**，绝不「出错就放过」。
4. **纵深防御**：不指望单一防线——参数化查询、最小权限、审计日志各管一层。

## 攻击面自查

### 1. 机密管理

```text
❌ const apiKey = "sk-proj-xxxx"          // 硬编码进源码
❌ db: "postgres://user:password123@..."  // 连接串带明文密码
✅ const apiKey = process.env.API_KEY     // 环境变量注入
✅ if (!apiKey) throw new Error("未配置 API_KEY")  // 启动期校验，快速失败
```

- [ ] 无硬编码的密钥、令牌、密码、私钥
- [ ] `.env` 类文件已在忽略清单中，且**历史提交里也没有**（改过就要轮换）
- [ ] 生产机密来自托管平台的机密管理，不随镜像/仓库分发
- [ ] 泄露过的密钥已轮换——删掉文件**不等于**吊销

### 2. 输入验证

- [ ] 所有外部输入（请求体、查询串、路径参数、上传文件、第三方回调）在处理前经模式校验
- [ ] 用**白名单**（允许什么）而非黑名单（禁止什么）
- [ ] 文件上传限制大小、类型、扩展名，且不只信 `Content-Type`；存储路径不可由用户拼出
- [ ] 校验失败返回明确的客户端错误，错误消息不泄露内部结构

### 3. 注入

```text
❌ query = `SELECT * FROM users WHERE email = '${email}'`   // 字符串拼接
✅ query("SELECT * FROM users WHERE email = $1", [email])   // 参数化占位
```

- [ ] 数据库访问全部参数化；**表名/列名/排序方向无法参数化时用白名单映射**，不要拼
- [ ] 命令执行、模板渲染、路径拼接、日志注入同样适用（不只 SQL）
- [ ] ORM 的「原生 SQL 逃生口」逐个看过——注入几乎都从那里进来

### 4. 认证与授权

- [ ] 令牌放 `HttpOnly` + `Secure` + `SameSite` Cookie，**不放** `localStorage`（XSS 可取）
- [ ] 每个敏感操作都有**对象级**鉴权：不只是「登录了吗」，而是「这个资源属于他吗」
- [ ] 越权自查：改 URL 里的 id、改请求体里的 ownerId，能不能读到别人的数据
- [ ] 权限判定失败返回 403，未认证返回 401，两者不混用
- [ ] 登出、改密、改邮箱后旧会话/旧令牌真正失效

### 5. 输出编码与 XSS

- [ ] 用户内容渲染前按上下文转义（HTML / 属性 / JS / URL 各有各的规则）
- [ ] 需要富文本时用成熟清理库 + 标签属性白名单，不自己写正则
- [ ] 配置内容安全策略（CSP）响应头，避免 `unsafe-inline`

### 6. CSRF

- [ ] 状态变更操作要求 CSRF 令牌，或依赖 `SameSite` Cookie + 自定义头
- [ ] 纯 Cookie 鉴权的接口不能只看「请求来自本站」

### 7. 速率限制

- [ ] 登录、注册、找回密码、验证码、搜索等接口单独限速，阈值比普通接口更严
- [ ] 限速维度覆盖 IP **和**账号，防止撞库分散到多 IP
- [ ] 限速**失败时拒绝**，不是放过

### 8. 敏感数据泄露

```text
❌ log("login", { email, password })          // 日志泄密
❌ res.status(500).json({ error: err.stack }) // 堆栈泄给用户
✅ log("login", { email, userId })            // 只记标识
✅ res.status(500).json({ error: "稍后重试" }) // 通用消息，细节只进服务端日志
```

- [ ] 日志与埋点中无密码、令牌、证件号、完整卡号；确需记录时只留后四位
- [ ] 错误响应不暴露堆栈、SQL、内部路径、依赖版本
- [ ] 传输强制 HTTPS；响应头含 CSP、`X-Content-Type-Options`、`X-Frame-Options`、HSTS
- [ ] CORS 白名单精确到来源，不用 `*` 配合凭据

### 9. 依赖与供应链

- [ ] 锁定文件已提交，CI 用锁定模式安装（`npm ci` 一类）而非浮动版本
- [ ] 依赖漏洞扫描通过，高危项已处理或有明确豁免理由
- [ ] 新增依赖前确认其维护状态与来源——引入包即引入信任

## 何时不用

- 纯内部、无外部输入的一次性脚本：流程走完即可，不必套全部清单。
- 框架已经默认做对的事（如 ORM 默认参数化）：核对一遍即可，不重复造轮子。

## 常见错误

| 错误 | 修正 |
|---|---|
| 只查「登录了吗」不查「能碰这条数据吗」 | 越权（IDOR）比未认证更常见，逐个资源核对归属 |
| 把校验放在前端 | 前端校验是体验，服务端校验才是安全；两边都要有 |
| 依赖删除文件来吊销密钥 | 密钥一旦进过仓库/日志就要**轮换**，删除不撤销暴露 |
| 错误处理里 `catch` 后继续放行 | 鉴权/校验的异常路径必须 fail closed |
| 只扫源码不扫历史提交 | 历史里的机密同样有效，需扫提交历史与构建产物 |

## 借口 vs 现实

| 借口 | 现实 |
|---|---|
| 「这是内部服务，不用鉴权」 | 内部服务一旦被横向移动利用就是最大的洞；内部只降低暴露面，不取消校验。 |
| 「输入前面已经校验过了」 | 校验必须在**信任边界处**做；跨层传递后无法证明上游一定校验过。 |
| 「密钥在 `.env` 里，没提交」 | 问的是「历史上提交过吗、日志里出现过吗、镜像里打包了吗」——三者任一为是即需轮换。 |
| 「用了 ORM 就不会注入」 | ORM 的原生 SQL 与拼接排序字段照样注入；要看的是逃生口。 |
| 「上线前再补安全」 | 认证与数据模型层面的缺陷越晚改越贵；写的时候就按边界划。 |
| 「这是测试环境，没关系」 | 测试环境的密钥配置、真实数据副本同样会外泄；配置纪律不分环境。 |
| 「加了限速就够了」 | 限速只防暴力枚举，防不了越权与注入——按攻击面逐项过，别拿一项顶全部。 |

## 红线自查

- [ ] 没有把「安全」推迟到上线前，而是写代码时就按信任边界划分？
- [ ] 每个涉及用户数据的操作都核对了**归属**，而不只是登录状态？
- [ ] 异常路径是拒绝（fail closed），没有静默放行？
- [ ] 机密既不在源码里，也不在历史提交与日志里？
- [ ] 报出的每个问题都说明了**可被怎样利用**，而不是泛泛「不安全」？
- [ ] 修复建议落到具体代码位置，而不是「加强安全意识」？
