# 写技能文档

## Overview

写 skill 是对流程文档做测试驱动开发：测试用例是施压场景，产品代码是 SKILL.md，测试失败是无 skill 时的违规基线，测试通过是有 skill 时 agent 照做，重构是堵新借口。

**核心原则：没看过 agent 在没有这个 skill 时怎么失败，就不知道这个 skill 教的东西对不对。**

**前置要求：先理解 dev-tdd 的红-绿-重构循环；本 skill 是同一循环在文档上的应用。**

## 何时建 skill

**建：** 这技巧当时对你并不显而易见；跨项目还会再次用到；模式通用、不绑定具体项目；别人也会受益。

**不建（换个地方放）：**
- 一次性方案 → 做完就完，不沉淀
- 外部文档已写清的标准实践 → 引用外部文档，不必复述
- 项目专属约定 → 写进项目说明文件，不进技能仓库
- 能用正则/校验器机械强制的约束 → 自动化它；文档只留给需要判断力的内容

## SKILL.md 结构规范

- 一个 skill 一个目录，目录里只放一个 SKILL.md，不建其他文件。
- frontmatter 只含 `name`（等于目录名，仅字母数字与连字符）与 `description` 两个字段；description 尽量 ≤500 字符。
- **description 值里出现英文冒号+空格（`: `）时必须整体用双引号包裹**：`description: "…Use when X: Y…"`。未加引号的纯量标量含 `: ` 会让严格 YAML 解析器报错，加载器**静默丢弃整个技能**——症状极具迷惑性：文件在、junction 通、lint 绿，就是这个技能永远不触发。已上线技能也适用：改完 description 要重新确认它仍出现在可用技能目录里。
- 正文用中文；代码、命令、字段名、报错信息保留英文。
- 正文 ≤200 行软上限；超了先想「是不是藏了两个意图」。
- 正文骨架（按需取用，不硬凑）：

```markdown
# 标题
## Overview      —— 这是什么，核心原则 1–2 句
## 何时使用      —— 症状/场景清单 + 何时不用
## 核心模式      —— 前后对比，最强示例放这里
## 快速参考      —— 表格，供扫读
## 常见错误      —— 出错点 + 修法
```

- 纪律型 skill 必带「常见借口 vs 现实」与「红线自查」两节；操作型必带「常见错误」节。
- 交叉引用只用已上线的技能名，并加显式强度标记（如 **REQUIRED BACKGROUND:** 先理解 dev-tdd）；不用会强制加载文件的路径写法。

## 发现性铁律：description 只写「何时使用」

description 只描述触发条件，**绝不概括 skill 的流程或方法**。

为什么是铁律：实测发现，description 一旦概括流程，agent 会拿它当捷径，照着它做而跳过正文——正文沦为被跳过的文档。真实案例：一条写着「任务之间做代码评审」的 description，让 agent 只做了一次评审，尽管正文流程图明确要求两次（先规格合规、后代码质量）；改成纯触发条件后，agent 才回去读流程图，按两段流程执行。

触发词写法：
- 含具体症状、场景、报错原文与关键词；写「问题」（如竞态、行为不一致），不写语言级表象
- 第三人称，不用第一人称
- 命名动词开头、主动语态：`condition-based-waiting` 优于 `async-test-helpers`

最佳示例（bad → good）：

```yaml
# ❌ 概括了流程 —— agent 会照它偷懒、跳过正文
description: Use when executing plans - dispatches subagent per task with code review between tasks

# ✅ 只有触发条件，没有流程
description: Use when executing implementation plans with independent tasks in the current session
```

## 铁律：先看失败，再写 skill

```
NO SKILL WITHOUT A FAILING TEST FIRST
```

对**新建**与**修改**同样适用。没看基线就动笔？删掉重来。改 skill 没跑测试？同罪。没有例外——不因「只是加一节」「只是文档更新」而豁免。

动笔前必须先回答：**没有这个 skill 时，agent 在这个任务上怎么失败？**

1. **基线观察**：在无 skill 状态下跑一遍任务，逐字记录 agent 的失败方式与辩解原话。
2. **触发冒烟测试（至少一次）**：说一句典型任务话（将来用户会说的原话），看命中的是不是这个 skill、命中后是否读了正文。新 skill 动笔前命中不了是正常的——这就是失败的测试；description 定稿后必须命中。命不中 → 先改 description，不是先改正文。
3. **纪律型加施压测试**：有子代理/后台代理工具则用它跑施压场景（时间压力 + 沉没成本 + 权威指令组合）；无则开一个不加载该 skill 的新会话复现，或逐条推演典型借口并核对正文是否有对应反制。
4. **对照组判定**：若不加载 skill 的对照组本来就不出现这个失败，说明没东西可修，别写这条指导。
5. **最小写作**：正文只针对观察到的具体失败写，不为假想情况加内容。
6. **回测与堵漏（REFACTOR）**：带 skill 重跑同一场景；出现新借口 → 加显式反制 → 再测，直到顶得住。

## 按失败类型选写法

写约束条款前，先给基线失败分类——对一类失败有效的形式，对另一类会帮倒忙：

| 基线失败 | 用对的形式 | 用错的形式 |
|---|---|---|
| 压力下明知故犯（懂规则但顶不住） | 禁令 + 借口对照表 + 红线自查 | 软建议（"prefer…"、"consider…"） |
| 照做了但产物形状不对（冗长、结论被埋） | 正面配方：按顺序写清产物「是什么」 | 禁令清单（"don't"、"never"） |
| 漏掉本该有的必备元素 | 在模板里留 REQUIRED 槽位 | 模板旁的散文提醒 |
| 行为应随条件而变 | 以可观察谓词为键的条件句（「若有 spec 则引用之」） | 无条件规则 + 豁免条款 |

禁令为何帮倒忙：存在竞争性激励时，agent 会跟「别 X」讨价还价；正面配方没有讨价还价的空间——产物要么符合所述形状，要么不符合。

无论选哪种形式：
- **不写微妙条款**：「除非很重要否则别 X」会重新打开讨价还价空间；真例外单独写成以可观察谓词为键的条件句。
- **豁免条款圈不住范围**：「此限制不适用于代码块」仍会抑制代码块；要让某部分豁免，就重写结构让规则够不到它。

## 测试类型速查

| 类型 | 例 | 测什么 | 过关标准 |
|---|---|---|---|
| 纪律型（强制规则） | 工作流纪律、完工前验证 | 学术题（懂规则吗）+ 施压场景（顶得住吗）+ 组合压力；抓借口加显式反制 | 最大压力下仍守规则 |
| 技巧型（操作方法） | 调试技巧、等待模式 | 新场景应用、边界变体、缺信息时找指令缺口 | 新场景能正确应用 |
| 模式型（思维模型） | 复杂度削减、信息隐藏 | 识别（认得出该用吗）、应用、反例（知道何时不该用） | 认得出、用得上、知反例 |
| 参考型（文档/速查） | API 文档、命令手册 | 检索（找得到吗）、应用、缺口测试（常用场景覆盖了吗） | 找得到并用得对 |

## 常见借口 vs 现实

| 借口 | 现实 |
|---|---|
| 「这 skill 一眼就懂，不用测」 | 你懂 ≠ 其他 agent 懂。测。 |
| 「只是个参考文档」 | 参考也有缺口和含混。测检索。 |
| 「测试太杀鸡用牛刀」 | 没测过的 skill 一定有问题；15 分钟测试省后面数小时。 |
| 「出了问题再测」 | 问题就是 agent 用不了这个 skill。上线前测。 |
| 「太繁琐，没空测」 | 在生产里调试一个坏 skill 比测试更繁琐。 |
| 「我有信心它没问题」 | 过度自信恰恰保证有问题。照测。 |
| 「通读一遍觉得没问题」 | 读过 ≠ 会用。测应用场景。 |
| 「批量写完一起测更高效」 | 部署没测过的 skill = 部署没测过的代码；一个测完再下一个。 |

## 红线自查

动笔前后逐条核对：

- description 里出现任何流程/方法概括 → 删掉，只留触发条件
- 没做过触发冒烟测试就写了正文 → 先补测试再改稿
- 纪律型 skill 没跑施压场景、缺借口对照表或红线自查节 → 不许上线
- 正文条款在防「假想的失败」而非测试中真实观察到的失败 → 砍掉
- 改 skill 前没看基线 → 同违规，删了重来
- 跳过测试的任何理由 → 上面的借口表已经答复过了

**任何一条命中：停下，先补失败观察，再回来改。**

## 常见反模式

- ❌ **叙事化经历**：「那次会话我们发现 projectDir 为空导致……」——太具体，不可复用
- ❌ **多语言示例稀释**：同一示例 js/py/go 各写一份——平庸且难维护，留一个最好的
- ❌ **流程图里塞代码**：节点写 `import fs`——复制不了、难读；代码进代码块，流程图只放决策
- ❌ **无语义标签**：`step1`、`helper2`——标签要有语义
