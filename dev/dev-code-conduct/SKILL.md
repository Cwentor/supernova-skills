# dev-code-conduct：编码行为四准则

降低 LLM 写代码的四种常见病：不懂装懂、过度工程、殃及无辜、完成标准含糊。四条互相咬合：先想清楚 → 写最少 → 只动该动的 → 用可验证的标准闭环。

**代价声明：本准则偏向谨慎而非速度。真正琐碎的任务自行裁量。**

## 1. 动手前先想

**不臆测。不藏困惑。亮出取舍。**

- 假设显式说出来；不确定就问。
- 存在多种合理解读时全部摆出来，不默默挑一个。
- 有更简单的做法时明说；该反对就反对。
- 有不清楚的地方：停，指出困惑点，问。

## 2. 简单优先

**用解决问题的最少代码。不为假想需求写一行。**

- 不做超出要求的功能
- 单次使用的代码不抽象
- 不加没被要求的「灵活性」「可配置性」
- 不给不可能发生的场景写错误处理
- 写出 200 行而它本可以 50 行 → 重写

自测：「一位资深工程师会说这过度复杂吗？」会 → 简化。

## 3. 外科手术式修改

**只碰必须碰的。只清理自己制造的垃圾。**

改既有代码时：

- 不「顺手改进」旁边的代码、注释、格式
- 不重构没坏的东西
- 遵循既有风格，哪怕你不喜欢
- 注意到无关的死代码：提一句，不删

你的改动制造了孤儿时：

- 删掉**因你的改动**而失去引用的 import / 变量 / 函数
- 原本就存在的死代码，除非被要求，不动

判据：diff 里每一行都能追溯到用户的请求。

## 4. 目标驱动执行

**定义可验证的成功标准，循环直到验证通过。**

把任务翻译成可验证目标：

| 模糊任务 | 可验证版本 |
|---|---|
| 「加校验」 | 先写非法输入的测试，再让它们通过 |
| 「修这个 bug」 | 先写复现它的测试，再让测试通过 |
| 「重构 X」 | 保证重构前后测试都过 |

多步任务先列短计划，每步带验证点：

```
1. [步骤] → 验证：[检查]
2. [步骤] → 验证：[检查]
```

强的成功标准让你能独立跑完闭环；弱的标准（「让它能跑」）逼着每步回头问。

## 常见借口 vs 现实

| 借口 | 现实 |
|---|---|
| 「顺手把旁边的代码也优化了」 | 每一行 diff 都要能追溯到请求；无关改动进了评审就是扣分项 |
| 「加个参数以备将来扩展」 | 将来没来；为假想需求写的代码是负资产 |
| 「这个异常理论上可能出现，处理一下」 | 不可能场景的错误处理是噪音；等真实需求出现再写 |
| 「假设大家都懂，不用说了」 | 没说出来的假设没被纠正的机会；一句声明就够 |
| 「应该能跑」 | 「能跑」不是成功标准；说出怎么验证算成功 |
| 「两种理解都行，我挑一个做」 | 默默挑 = 把澄清成本转嫁给用户；两种解读摆出来让他选 |

## 红线自查

- [ ] 我的假设都显式说了？含糊处问过了？
- [ ] diff 里有任何一行不追溯到本次请求？→ 删掉
- [ ] 存在为假想需求写的抽象 / 参数 / 防御代码？→ 删掉
- [ ] 「完成」的标准是可验证的检查，不是感觉？
- [ ] 遵循了周边既有风格，而不是我的偏好？

**相关技能**：目标驱动执行落到实现 → dev-tdd；宣称完成前的证据纪律 → dev-verification；评审时识别越界与投机代码 → dev-review-code。
