# dev-code-conduct：编码行为四准则

本件是**基线层**：不单独承接任务，只规定做任务时的行为底线。四种病、四道反制，依次咬合——先把话问明白，再写最少的代码，只动该动的地方，最后用可验证的标准收口。

| 病 | 长什么样 | 反制 |
|---|---|---|
| 不懂装懂 | 猜着往下写，把疑问咽回肚子里 | 先想 |
| 过度工程 | 为「将来可能要」提前写代码 | 写最少 |
| 殃及无辜 | 顺手改了跟本次无关的东西 | 只动该动的 |
| 完工含糊 | 「应该能跑」就当作完成 | 可验证收口 |

**代价声明：本准则拿速度换确定性。任务确实琐碎时自行裁量。**

## 一、先想：疑问要摆在动手之前

- **假设写出来**。留在脑子里的假设，别人没有机会纠正它。
- **多种解读并存就全摆出来**，不要默默挑一个执行——默默挑等于把澄清成本转嫁给对方。
- **看到更省事的路就直说**；该反对时反对，不要先照做着看。
- **卡住就停下**，指出卡在哪、缺什么信息，而不是绕过去继续写。

判据：动手之前，能用一两句话讲清「我打算改什么、为什么是这个改法」。讲不清，说明还没想完。

## 二、写最少：只解决被提出的问题

- 只做被要求的，不附送功能
- 只用一次的东西不抽成抽象
- 没被要求的「灵活性」「可配置性」不加
- 不可能出现的场景不写防御代码
- 写完回头看：**删掉一半还能跑吗？** 能，就继续删到不能再删

自测：一位资深工程师看到这段，会说「想多了」吗？会，就简化。

## 三、只动该动的：把改动限制在请求范围内

改既有代码时：

- 不「顺手」美化旁边的代码、注释或格式
- 不重构没坏的东西
- 跟随既有风格，哪怕自己更习惯另一种
- 发现无关的死代码：提一句，别删

改动自己制造了孤儿时：

- **因本次改动**而失去引用的 import / 变量 / 函数：清掉
- 本来就存在的死代码：没被要求就不动

判据：diff 里每一行都能指回本次请求。指不回去的，删掉。

## 四、可验证收口：把「做完」定义成一次检查

把任务翻译成能跑出真假的目标：

| 模糊说法 | 可验证版本 |
|---|---|
| 「加个校验」 | 先写非法输入的测试，再让它通过 |
| 「修这个 bug」 | 先写能复现它的测试，再让测试通过 |
| 「重构这块」 | 保证重构前后测试结果一致 |

多步任务先列短计划，每步带验证点：

```
1. [步骤] → 验证：[检查]
2. [步骤] → 验证：[检查]
```

判据：标准够强，就能不看人自己跑完闭环；不够强（「让它能跑」），每一步都得回头问一次。

## 常见借口 vs 现实

| 借口 | 现实 |
|---|---|
| 「顺手把旁边的也优化了」 | 指不回请求的改动，进评审是扣分项不是加分项 |
| 「加个参数，将来好扩展」 | 将来没来；为假想需求写的代码是负债 |
| 「这个异常理论上可能发生」 | 不可能场景的防御是噪音；等真遇到再写 |
| 「这么明显，不用说了」 | 没出口的假设没有被纠正的机会 |
| 「应该能跑」 | 能跑不是标准；说清用什么检查它算跑通 |
| 「两种理解都行，我挑一个」 | 交回去的成本是一句话，自己挑的成本是一次返工 |
| 「先写着，有问题再改」 | 方向错了，写得越多越难改回来 |

## 红线自查

- [ ] 动手前的假设、取舍、卡点，都出口了吗？
- [ ] diff 里有指不回本次请求的行？→ 删掉
- [ ] 有为假想需求写的抽象、参数或防御代码？→ 删掉
- [ ] 「完成」是一句可执行的检查，还是一种感觉？
- [ ] 跟的是周边既有风格，还是自己的偏好？
- [ ] 改动产生的孤儿（失去引用的 import / 变量 / 函数）清掉了吗？

**相关技能**：目标驱动执行落到实现 → `dev-tdd`；宣称完成前的证据纪律 → `dev-verification`；评审时识别越界与投机代码 → `dev-review-code`。
