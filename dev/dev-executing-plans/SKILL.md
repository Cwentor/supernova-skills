# 执行计划 / 票据 / 规格

计划已经替你想过：执行 = 忠实转录 + 测试证明，外加一份比你的记忆持久的记录。计划出自 dev-writing-plans，票据出自 dev-tickets，规格见 dev-spec；执行中每片走 dev-tdd；执行完接 dev-request-review；宣称完成前走 dev-verification。

## 模式选择（能力探测）

| 模式 | 做法 | 选择判据 |
|---|---|---|
| **inline** | 单会话自己逐任务干完，终审一次 | 兜底默认：无子代理/后台代理工具时自动落于此；计划完整、任务多为独立时够用 |
| **子代理逐任务** | 每任务派一个全新上下文的实现者 + 任务间评审 | 有子代理/后台代理（若有）且计划较长、后期任务会跑在已压缩的上下文上，或需要每任务评审门 |
| **并行分派** | 2+ 个独立无共享状态的任务同时跑 | 同上，能力探测；任务间有依赖或共享文件/状态 → 一律禁止并行 |

探测顺序：先问「有无子代理/后台代理工具」——没有 → inline，绝不假装分派；有 → 再问「任务是否互相独立、无共享状态」——是且 ≥2 个 → 并行分派，否则子代理逐任务串行推进。规格完整的计划就是转录 + 测试，低档模型即可；全程唯一值得最强模型的位置是终审。

## 通用纪律（所有模式）

- **台账优先于记忆**：每份计划一个 git 忽略的工作目录，`progress.md` 第一行写身份 `# ledger — plan: <计划路径>`。任务一完成就记 `Task <N>: complete (...)`，与提交同一批动作。上下文压缩或中断后，信任台账与 git log，不信任回忆：有完成行的任务不重做，从第一个没有完成行的任务恢复。第一行指向别的计划的台账不是你的，别动它。
- **裁决而非停摆**：冲突、歧义、计划缺陷，当场裁决，按格式记进台账再继续：`Ruling: <裁决> — <理由> — <错了的代价>`。未记账的偏离 = 秘密决策。spec 是权威，计划是它的论证，两者都没答的由你的判断定。
- **只有四类停机**：不可逆/破坏性操作；安全敏感动作；越出本工作区、按规范须先问的副作用（合并、推共享分支、发布）；计划烂到每条路都是猜。其余一律连续执行，不问「要不要继续」。
- **防上下文污染**：长输出（测试日志、diff、报告）写进文件，只读尾部或摘要；一切以指针传递（spec 路径、票据、笔记、提交号），不往上下文粘贴大段内容。

## 准备（所有模式）

1. 隔离工作区：参照 dev-git-worktrees；无 worktree 机制则至少开独立分支。未经用户明确同意，不在 main/master 上实现。
2. 读计划一遍，记下全局约束，每任务建一条进度项；计划指向 spec 就读 spec，冲突以 spec 为准。没有可读的 spec → 台账记一行，所有裁决视为临时。
3. 预检扫描：开工前扫任务间冲突——每个「后任务消费前任务产出」的接口记一行：两个任务、产出 vs 消费、发现；每个任务自身文本是否自洽（它规定的测试 vs 它规定的代码）。零共享接口就记 `Pre-flight: no shared interfaces`。对每条发现先裁决、记账，再开工。
4. 票据不是步骤清单，是**任务图**：阻塞关系决定顺序；任何时刻都存在一个可取的「前沿」（frontier），完成一件即解锁下一批。

## inline：单会话逐任务

每个任务走四步：

1. **取任务**：只读该任务的 brief——精确值、签名、测试用例只在 brief 里，「我记得」只是摘要。记下 BASE。
2. **走 dev-tdd 逐步干**：测试先写、亲眼看它失败、再实现。计划步骤自带 `Expected:` 的，跑了命令、读了输出、逐条比较。三种结果：匹配 → 下一步；**代码错** → 走 dev-debugging 找根因，绝不改测试或打补丁凑输出；**计划错** → 最小改动满足 spec，记 Ruling，带着裁决继续。
3. **完成契约**（写完成行前必须全真，证据在本会话）：brief 点名的测试都跑过、输出都读过；任务最终测试运行通过；每个 `Expected:` 都比较过；每处偏离都有 Ruling。
4. **记账**：`Task <N>: complete (commits <base7>..<head7>, tests: <command> → <result>)`。测试失败不记——任务未完成。节奏上：过程中常跑类型检查与单文件测试；每任务末跑一次该任务的测试；全套测试整个分支最后跑一次。按计划的提交步骤提交；计划没写就每任务一提交，提到当前分支。

## 子代理逐任务（有子代理/后台代理工具时）

**分派即构造上下文**——子代理永不继承你的会话历史，你给它什么它知道什么：

- 分派五要素：一行项目定位；brief 文件路径（需求唯一来源，精确值只在里面）；早前任务产出的接口与已做裁决；你已解决的歧义；报告文件路径 + 报告契约（完整报告写文件，只回状态/提交/一行测试摘要/疑虑）。brief 步骤已是 RED-GREEN 顺序，要求实现者按 dev-tdd 执行并自审。
- 同型小批量合并：几个同形的一行修正/常量变更，合成一次分派、一份 diff 评审。实现者永不自带评审——评审由你在报告之后发起，实现者自起的评审是重复席位，当缺陷记录。
- 状态处理：DONE → 打包评审；DONE_WITH_CONCERNS → 先读疑虑再定；NEEDS_CONTEXT → 补上下文重派；BLOCKED → 缺上下文就补、能力不够就升档、任务过大就拆、计划本身错就先裁决再带着裁决重派。
- 模型档位：机械转录最便宜档；跨文件集成中档；架构与终审最强档；修复循环 4–5 轮比原实现者升一档。回合数比单价贵——最便宜的模型常花 2–3 倍回合。

**每任务评审**（不可跳；实现者自审替代不了）：评审输入 = brief + 报告文件 + diff 包（`BASE..HEAD` 落成文件；BASE 用分派前记的，不用 `HEAD~1`）+ 逐字复制的全局约束。分派词里出现「别报 X」「最多算 Minor」= 预判结论，为自己免掉评审轮，违规。评审报「无法从 diff 验证」的项由你裁决——你才有跨任务上下文。

**修复循环**：上限 5 轮；一轮 = 一次修复分派 + 一次范围化复审（复审只逐条裁决 ADDRESSED / NOT ADDRESSED，外加修复 diff 内新引入的 Critical/Important 破坏）。1–3 轮唤醒原实现者（上下文还在）；4–5 轮换新实现者并升档。主会话自己不动手修——绕过评审且污染协调上下文。

**断路器**：第 5 轮仍不干净 → 停止分派，逐条裁决：评审错了或可争议 → 搁置（park）并记 Ruling；真实但无下游依赖 → 同样搁置；真实且承重（后续任务建在其上）→ 裁决最小解阻改动，记账，带进下一任务的分派。静默丢弃 = 违规；仅在缺陷让每条路都成猜时才停机问人。

## 并行分派（2+ 独立任务）

- **全部满足才并行**：不同根因/不同子系统；互不依赖；无共享状态、不改同一批文件；互不干扰。修一个可能连带修复其他、需要全局系统视野、还在探索式定位 → 不并行。
- **一个问题域一个代理**，同一批分派一起发出即并行；有后台运行就让实现者后台跑，保持最大并发，前沿一更新就立即补位。有条件时每个实现者独立 worktree/分支，完成后逐一合并回工作分支（参照 dev-git-worktrees）。
- **提示词四要素**：具体范围（哪个文件/子系统）、明确目标（让哪些测试过）、约束（不许改哪些代码；「不要只调大超时，找真问题」）、规定输出（返回根因 + 改动摘要）。
- **返回后整合**：逐份读摘要；查是否改了同一处；跑全套；抽查——代理会犯系统性错误。

## 终审与宣称完成

1. **全分支终审**：`MERGE_BASE..HEAD` 打成一个 diff 文件。有子代理/后台代理（若有）→ 用可用最强模型分派终审，走 dev-request-review，连同台账里的搁置项与 Minor 清单交给它分诊；没有 → 按 dev-request-review 的标准自己审，台账写明 `Final review: self-review`，并告知用户这是作者自审，由用户决定是否够格。
2. **重分级再动手**：评审标签只是建议；按「发布后普通用户实际承受什么」重评。Critical/Important → **一轮**修复：每个修复走 dev-tdd——写复现测试、看它 RED、修 GREEN、全套过，记账 `Final: fixed <发现> — <测试名> RED→GREEN, suite <N>/<N>`。Minor → 台账 `Final: minor (deferred): <一行>`，永不进修复轮；不修的发现是 Ruling，进最终报告。没有第二轮修复，不重派再审。
3. **宣称完成前走 dev-verification**：类型检查、全套测试、真实输出都读完，才许说「完成」。
4. **收尾**：终审干净且修复已提交 → 删除本计划工作目录（git 历史即记录）；把所有 Ruling 与搁置 Minor 汇成完整清单交用户；走 dev-finish-branch。

## 红线自查（每次宣称「完成」前逐条过）

- 有没亲眼见过失败的测试就放行？→ 未证明。
- 有未记账的计划偏离？→ 秘密决策。
- 台账落后于实际进度？→ 压缩后必重做。
- 并行任务间共享状态或依赖未排除？→ 停。
- 把「应该会过」当证据？→ 要命令 + 输出。
- 评审未回就进下一任务？→ 未验证的推进。
- 静默丢弃过评审发现？→ 违规。

## 借口表

| 借口 | 现实 |
|---|---|
| 「我记得任务 N 写了什么」 | 你记得的是摘要；精确值在 brief 里，读它。 |
| 「改动很小，测试应该会过」 | 「应该」不是证据；契约要命令和输出。 |
| 「计划错了，我直接按对的来」 | 按对的来 + 记 Ruling；不记 = 秘密决策。 |
| 「过几个任务再一起补台账」 | 压缩不挑时间；每任务一行，与提交同批。 |
| 「问一下要不要继续」 | 选自动执行就是为了少打扰；只有四类停机。 |
| 「我读自己的 diff 很仔细，终审多余」 | 同一作者同一盲区；终审是全程唯一新鲜视角。 |
| 「逐任务太慢，终审也省了吧」 | 全分支一次终审是下限，不是上限。 |
| 「评审标 Minor 那就是 Minor」 | 标签评的是 spec 的沉默；按用户实际承受重评。 |
| 「修复很明显，不用先写失败测试」 | 失败测试是发现真实存在且已消除的唯一证据。 |
| 「顺手把 Minor 也修了」 | 每个 Minor 都是用户没要的测试+修复+全套；记账，用户定。 |
| 「再修一轮总会收敛」 | 过了上限不收敛，失败是结构性的；裁决并改道。 |
| 「反正复审还会挑新毛病」 | 范围化复审只能核对修复；未动代码的新发现进台账，不进循环。 |

## 示例（inline 一瞥）

```
[探测：无子代理工具 → inline；预检 2 行共享接口、1 条裁决已记账]
Task 1: 安装钩子脚本
  [失败测试 → FAIL: install_hook not defined（符合 Expected）]
  [实现 → PASS 1/1；commit d4e5f6a]
  [台账] Task 1: complete (commits a1b2c3d..d4e5f6a, tests: npm test -- hooks → 1/1 pass)
Task 2: 恢复模式
  [失败测试 import 报错：Task 1 实际导出 installHook，brief 写 install_hook]
  [Ruling: install_hook → installHook — 与 Task 1 产出一致 — 错了付一次重命名]
  [台账] Task 2: complete (commits d4e5f6a..b7c8d9e, tests: npm test -- recovery → 8/8 pass)
[全部任务后] diff 包 MERGE_BASE..HEAD → 终审（最强模型；无工具则自审并声明）
[终审 1 条 Important： 进度上报间隔硬编码]
[修复] test_progress_interval_configurable RED → 提取 PROGRESS_INTERVAL → GREEN → suite 12/12
[台账] Final: fixed hardcoded interval — test_progress_interval_configurable RED→GREEN, suite 12/12
[裁决清单 + 搁置 Minor 交用户] → dev-verification → dev-finish-branch
```
