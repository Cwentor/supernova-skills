# 测试驱动开发（TDD）

## 概述

先写测试，看它失败，再写最少的代码让它通过，最后清理。

**核心原则：** 没亲眼看到测试失败，就不知道它测的是不是对的东西。

**违反规则的字面，就是违反规则的精神。**

## 铁律

```
NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST
```

代码先于测试写出来了？删掉，从测试开始重来。

**没有例外：**
- 不许留作「参考」
- 不许边写测试边「改编」它
- 不许看它
- 删除就是删除

从测试出发重新实现。

## 何时使用

**一律使用：** 新功能、修 Bug、重构、行为变更。

**例外（需用户明确同意才可跳过）：** 一次性原型（配合 dev-prototype）、生成的代码、纯配置文件。

想着「就这一次跳过 TDD」？停——那是借口，见下方对照表。

## 红绿重构循环

每一轮：**RED**（失败测试）→ 验证失败 → **GREEN**（最少代码）→ 验证通过 → **REFACTOR**（清理）→ 下一轮。

### RED：写失败测试

一个循环只测一个行为：

- 测试名描述行为（读得出「什么能力应该存在」）；名字里出现「和」就拆分
- 断言真实代码的行为，万不得已才 mock
- 预期值来自独立事实：已知字面量、规格、手算结果——不许用实现同款算法现算一遍

**验证 RED（必做，不许跳过）：** 运行该测试，确认三件事：

- 测试是**失败**，不是报错
- 失败信息正是预期的失败
- 失败原因是要做的功能不存在，不是笔误

测试直接通过？你在测既有行为——修测试。测试报错？先修报错再重跑，直到它「正确地失败」。

### GREEN：最少代码

写刚好让测试通过的代码。不加投机功能、不顺手重构、不「改进」测试之外的地方。

**验证 GREEN（必做）：** 重跑，确认：

- 该测试通过
- **整个项目套件**通过：收尾前运行项目完整测试命令；任何失败——包括不是你造成的——都要在报告里点名
- 输出干净：无 error、无 warning

测试失败？修代码，不是修测试。

### REFACTOR：清理

只在全绿之后：消除重复、改进命名、提取辅助函数。保持测试绿，不加新行为。

### 重复

下一个行为，从下一个失败测试开始。

## 测试写在哪个层级

TDD 循环在**能表达该行为的最低层**写测试；高层留给真正跨层协作的行为：

| 层级 | 测什么 | 特点 |
|------|--------|------|
| 单元测试 | 纯函数、工具类、组件逻辑、辅助函数 | 快、完全隔离；绝大多数循环住在这层 |
| 集成测试 | API 端点、数据库操作、服务间交互、外部调用 | 验证组件组合后的真实行为 |
| E2E 测试 | 关键用户流程、完整工作流、UI 交互 | 最接近用户，也最慢最脆；只给真正要紧的流程 |

- 循环用低层拿快反馈，收尾用高层确认关键流程；高层慢而脆，不做主反馈回路
- 每个测试自设数据、自清理；测试之间互不依赖、互不影响

## 接缝：测试站在哪里

**接缝（seam）**是观察行为的公共边界。测试只站在接缝上，从不伸进实现内部。三种反模式：

- **实现耦合**：mock 内部协作者、测私有方法、绕过接口从旁路（直接查库）验证。判据：重构后行为没变，测试却挂了
- **同义反复**：断言用实现同款算法重算预期值——构造性通过，永远抓不到 bug
- **横向切片**：先写完全部测试再写全部实现——验证的是想象中的行为。改用**垂直切片**：一个测试 → 一段实现 → 重复

测试力气有限：范围大或拿不准时，先写下打算测的接缝，与用户对齐；接口形状本身存疑（模块多深、边界在哪）时，用 dev-codebase-design 的词汇表讨论。项目若有术语表/领域文档，测试命名与其领域语言保持一致。

## 覆盖率（可选条款）

项目设有覆盖率门禁（配置里写明阈值、CI 会卡）时：遵循该门禁，收尾前运行覆盖率命令（如 `npm run test:coverage`）确认达标。项目没有门禁时不追指标，以「关键路径、边界、错误路径都有测试」为完成标准。

## 示例：修 Bug

**Bug：** 空邮箱被提交接受。

**RED**
```typescript
test('rejects empty email', async () => {
  const result = await submitForm({ email: '' });
  expect(result.error).toBe('Email required');
});
```

**验证 RED**
```bash
$ npm test
FAIL: expected 'Email required', got undefined
```

**GREEN**
```typescript
function submitForm(data: FormData) {
  if (!data.email?.trim()) {
    return { error: 'Email required' };
  }
  // ...
}
```

**验证 GREEN**
```bash
$ npm test
PASS
```

**REFACTOR：** 多个字段都需要校验时，提取校验辅助函数；保持绿。

## 常见借口 vs 现实

| 借口 | 现实 |
|------|------|
| 「太简单不用测」 | 简单代码也会坏，测试只花 30 秒 |
| 「我后补测试」 | 后补的测试一写就过，什么也证明不了；没看过它失败，就没证明它抓得住 bug |
| 「后补测试目标一样，重要的是精神不是仪式」 | 后补回答「它做了什么」，先行回答「它该做什么」；后补被已写的代码带偏，只验证你记得的情形 |
| 「已经手动测过了」 | 手动测试无记录、无法重跑、压力下必漏；「我试过没问题」≠ 覆盖全面 |
| 「删掉 X 小时的工作太浪费」 | 沉没成本；真选择是带着测试重写（高信心）vs 留着不信任的代码（大概率有 bug）——留着才是浪费 |
| 「留作参考，测试先写」 | 你会忍不住改编它——那就是后补测试。删除就是删除 |
| 「得先探索一下」 | 可以，探索完丢掉探索代码，从 TDD 重新开始 |
| 「测试难写，说明不用 TDD」 | 听测试的：难测就是难用，是设计信号，简化接口 |
| 「TDD 太慢，不务实」 | 「务实」捷径意味着在生产里调试——那才慢；TDD 在提交前抓 bug，让你敢重构 |
| 「手动验证更快」 | 手动验证不了边界，且每次改动都要人工重来 |
| 「存量代码本来就没测试」 | 那正是你要改善的：为改到的存量代码补测试 |

## 红线自查

抓住自己在想/说以下任何一条：停下，删代码，从测试重来：

- 代码先于测试
- 实现写完才补测试
- 测试一写就通过
- 说不出测试为什么失败
- 测试「以后再加」
- 「就这一次」「我已经手动测过了」「后补测试效果一样」
- 「重要的是精神不是仪式」「留作参考」「改编现有代码」
- 「已经花了 X 小时，删了可惜」「TDD 太教条，我这是务实」「这次不一样，因为……」

宣称完成前逐项核对，缺任何一项 = 跳过了 TDD，重来：

- [ ] 每个新函数/方法都有测试
- [ ] 每个测试都先看过它失败，且失败原因正确（功能缺失，非笔误）
- [ ] 每次都只写了让测试通过的最少代码
- [ ] 全项目测试通过，输出干净（无 error、无 warning）
- [ ] 测试用真实代码（万不得已才 mock）
- [ ] 边界与错误路径都有测试

## 卡住时

| 问题 | 对策 |
|------|------|
| 不知道怎么测 | 写你**希望存在**的 API，先写断言；再不然问用户 |
| 测试太复杂 | 设计太复杂，简化接口 |
| 什么都得 mock | 代码耦合太重，用依赖注入 |
| 测试铺垫巨大 | 提取测试辅助函数；仍然巨大 → 简化设计 |

## 与其他技能的关系

- 修 Bug：先用失败测试复现 bug（回归测试），再走循环 → dev-debugging
- 宣称「完成/全绿」前，实际运行验证命令并引用真实输出 → dev-verification
