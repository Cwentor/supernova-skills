# dev-triage：外来 issue 的分诊状态机

把**外来** issue——bug 报告、他人需求、未经加工的请求——沿一个小的角色状态机推进：分类 → 验证 → 必要时深挖 → 产出 agent 可直接认领的 brief。维护者用自然语言下指令，你解释并执行。

**边界（易混，先读）：**

- 只分诊**外来**请求。本仓 dev-tickets 拆出的票据**已经 agent-ready，不要再分诊**，直接进执行流程；dev-spec 发布的规格同理（已带就绪标签）。
- 需要先把设计讨论谈透而非处置存量的，转 dev-brainstorming。
- 请求面是否包含外部 PR 由项目配置决定；包含时，**PR 就是一个带代码的 issue**：同一套角色、状态、流程，只是「验证」对 diff 做，brief 的任务是完成/补齐现有代码而非从零建。

## 本仓配置（分诊前先读；没有就用默认）

- **Issue tracker**：有真实 tracker 工具（CLI / API）→ 在原生 issue 上改标签、发评论；没有 → 本地 tracker，一票一个 markdown 文件放项目约定目录，标签写进票面（如 `Labels: bug, needs-triage`）。
- **标签词表**：状态角色规范名 `needs-triage` / `needs-info` / `ready-for-agent` / `ready-for-human` / `wontfix`；类别角色 `bug` / `enhancement`。项目 tracker 已用别名（如把 `needs-triage` 写作 `bug:triage`）时**套用既有标签**，不另造重复标签。
- **领域文档**：默认单上下文——根 `CONTEXT.md` + `docs/adr/`；多包仓库可改多上下文——根 `CONTEXT-MAP.md` 指向各子上下文。分诊全程用其词汇、尊重其 ADR。

## 角色与状态机

- **类别**（恰好一个）：`bug`（有东西坏了）/ `enhancement`（新功能或改进）。
- **状态**（恰好一个）：`needs-triage` 待维护者评估；`needs-info` 等报告者补信息；`ready-for-agent` brief 已附、agent 可认领；`ready-for-human` 需要人做（判断、外部权限、设计抉择、手工测试）；`wontfix` 不处理。

迁移路径：未打标 → `needs-triage` → 其余四种状态；报告者回复后 `needs-info` → `needs-triage`。类别或状态出现冲突 → 先向维护者标记求证，再做任何动作。维护者可随时否决；见到异常迁移，先确认再动。

## AI 声明

分诊期间发出的每条评论 / issue，**必须**以这行开头（让人知道这是 AI 生成的）：

```
> *This was generated by AI during triage.*
```

## 列出需要注意的

查询后按三个桶展示（桶内最老在前）：**未打标**（从未分诊）；**`needs-triage`**（评估中）；**`needs-info` 且报告者在上次分诊后有新动静**（需重评）。PR 在请求面内时按外部来源过滤并列，每行标注 `[issue]` / `[PR]`；显式点名的 PR 不论作者一律分诊。给计数和每条一行摘要，让维护者挑。

## 分诊一条 issue / PR

1. **收集上下文。** 读全文：正文、评论、标签、作者、日期（PR 加 diff）。解析既有的分诊记录，**不重问已解决的问题**。用领域词汇探索相关代码。跑两个对照检查：(a) **重复实现**——按领域概念（不是报告者的措辞）搜既有实现，命中即「已实现型 wontfix」；(b) **曾被拒绝**——读项目的 out-of-scope 记录（如有 `.out-of-scope/*.md`，一概念一文件），按概念相似度匹配（「夜间主题」能撞上 `dark-mode.md`），有匹配先亮给维护者。

2. **给建议。** 报出你建议的类别 + 状态及理由，附一段与请求相关的代码库摘要（含是否已实现）。等维护者定夺。

3. **验证主张。** 拷问之前先核实：bug 按报告者的步骤复现；PR 拿到 diff 后确认名副其实，跑相关测试 / 命令。报告结果：**确认**（附代码路径）/ **复现失败** / **信息不足**。信息不足是 `needs-info` 的强信号；确认过的主张写出的 brief 坚实得多。

4. **必要时深挖。** 请求需要打磨时，逐轮提问拷问成形，边落决策边沉淀领域词汇与 ADR（有 dev-brainstorming / dev-domain-modeling 技能则配合用之，无则自己逐轮问）。

5. **落状态。**
   - `ready-for-agent`：发 agent brief（见下节）。
   - `ready-for-human`：同样结构，注明为何不能委托。
   - `needs-info`：发分诊记录（模板在下）。
   - `wontfix`：关闭，评论按原因分三种——**已实现**：指出现存位置，**不要**写 out-of-scope 记录（那是拒绝的归档，不是建成的归档）；**拒绝的 bug**：礼貌解释后关闭；**拒绝的 enhancement**：写 / 更新 out-of-scope 记录（决策 + 实质理由——范围哲学、技术约束、战略取舍，不写临时借口——+ 历次请求链接），评论链过去再关闭。
   - `needs-triage`：打上标签；有部分进展可留一条评论。

维护者说「直接把 #42 移到 X」时：照办，先复述一遍将做的动作（改标签、评论、关闭）再执行，跳过拷问；未经拷问直进 `ready-for-agent` 的，问一句要不要补一份 brief。

Issue 上已有分诊记录时（恢复中断的分诊）：先读之，核对报告者此后回答了哪些悬而未决的问题，给更新后的全貌再继续。

### needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**
- 已谈定的全部落在这里，别让拷问成果蒸发

**What we still need from you (@reporter):**
- 问题 1：具体、可行动（不许写「请提供更多信息」）
- 问题 2
```

## Agent Brief（本 skill 的核心产物）

brief 是贴在 issue 上的**权威规格**；原正文与讨论只是上下文。四原则：

1. **耐久高于精确**：issue 可能在 `ready-for-agent` 躺几周，代码库一直在动。写接口、类型、行为契约；**不写**文件路径与行号，不假设当前实现结构不变。
2. **行为式而非过程式**：写系统**该做什么**，不写怎么实现——agent 会自己探索代码库。好：「`SkillConfig` 类型应接受可选 `schedule` 字段（类型 `CronExpression`）」；坏：「打开某文件第 42 行加个字段」。
3. **验收标准完备**：每条独立可验证。好：「`gh issue list --label needs-triage` 只返回已初分类的 issue」；坏：「分诊功能正常工作」。
4. **显式划出 Out of scope**，防镀金、防越界。

```markdown
## Agent Brief

**Category:** bug / enhancement
**Summary:** 一句话，要发生什么

**Current behavior:** 现状（bug 的坏行为 / enhancement 的出发点）
**Desired behavior:** 完成后应有的行为，含边缘与错误情形
**Key interfaces:** 要改的类型 / 函数签名 / 配置形状，及原因
**Acceptance criteria:**
- [ ] 具体、可测的标准
**Out of scope:**
- 不该动的、看似相关的邻接功能
```

（PR 的 brief 同构：「Current behavior」描述 diff 现状，任务是完成 / 补齐它。）

## 常见错误

- 不验证就信报告者的话，把复现不了的 bug 推进 `ready-for-agent`。
- 重问分诊记录里已解决的问题，烧光报告者的耐心。
- brief 写成过程式指令（文件 + 行号），issue 躺两周后尽数失效。
- 把「已实现」的 wontfix 写进 out-of-scope 归档，污染去重检查。
- 类别或状态漏挂、双挂，下游无法判断下一步。
- 忘贴 AI 声明。

## 红线自查（落状态前过一遍）

- [ ] 确认这是外来请求；若为本仓 dev-tickets 票据或 dev-spec 规格，停下交还执行流程。
- [ ] 类别与状态各恰好一个，迁移路径合规。
- [ ] 重复实现与曾被拒绝两项对照检查都跑过。
- [ ] 拷问之前验证过主张（或明确记为 `needs-info`）。
- [ ] brief 无文件路径 / 行号，验收标准逐条可独立验证。
- [ ] 每条发出的评论都带 AI 声明。
