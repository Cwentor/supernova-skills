# 编写实施计划

## 定位与边界

- 已有规格/需求（通常经 dev-brainstorming 讨论、按 dev-spec 沉淀），下一步是把它变成可执行计划：**先写计划，再写代码**。
- 规格覆盖多个独立子系统时，退回拆成多份子规格、每子系统一份计划；每份计划必须独立产出可运行、可测试的软件。
- 计划写完交 dev-executing-plans 逐任务执行；本技能只产出计划，不实现。

## 核心假设：执行者零上下文

把执行者当作「技术过硬，但对你的代码库、工具链、领域几乎一无所知，也不擅长设计测试」的工程师。计划必须自包含到执行者无需再做任何设计决策：

- 每个任务写明改哪些文件（精确到行）、贴出实际代码、给出验证命令与预期输出。
- 原则：DRY、YAGNI、TDD、频繁提交。
- 保存到 `docs/plans/YYYY-MM-DD-<feature-name>.md`（用户指定路径优先）。

## 文件结构先行

定义任务前，先画出要创建/修改的文件及各自职责——分解决策在这里锁定：

- 单一职责、清晰边界、明确接口。
- 优先小而专注的文件；一起变化的文件放在一起；按职责拆分，不按技术分层。
- 存量代码库遵循既有模式，不擅自重构；但若你要改的文件已臃肿，把拆分纳入计划是合理的。

## 任务切分

- 任务 = 自带一轮测试周期、值得单独过一次评审门的最小单元。
- 搭建、配置、脚手架、文档步骤并入需要它的那个任务；只有当评审者可能拒绝 A 却放过 B 时才切开。
- 每个任务以可独立验证的交付物收尾。

## 步骤粒度

每步一个动作（2–5 分钟），每步一个可勾选项：写失败测试 → 跑它确认失败 → 最小实现 → 跑测试确认通过 → 提交。

## 计划文档头模板

```markdown
# [功能名] 实施计划

> 本计划交 dev-executing-plans 逐任务执行；步骤用 `- [ ]` 勾选跟踪。

**Goal:** [一句话：构建什么]

**Architecture:** [两三句：采用的方案]

**Tech Stack:** [关键技术/库]

**Spec:** [本计划所实现规格的路径——计划从规格出发论证，执行者需同时读两者]

## Global Constraints

[规格中的全局要求：版本下限、依赖限制、命名/文案规则、平台要求——每条一行、逐字抄自规格。所有任务默认隐含本节。]

## Review Focus

[规格隐含但没有任何任务的测试覆盖的输入类别/失效模式，取最可能咬到真实使用者的前五条，每条一行：输入或条件 + 合理预期的行为，最可能在前。规格是愿景文档：它规定软件必须做什么，不枚举它会遇到的一切；对某输入沉默不等于允许它搞崩程序。在此一次性列全，再为每条补一个测试，挂到拥有该代码的任务。]
```

## 任务模板（最佳示例）

````markdown
### Task N: [组件名]

**Files:**
- Create: `exact/path/to/file.py`
- Modify: `exact/path/to/existing.py:123-145`
- Test: `tests/exact/path/to/test.py`

**Interfaces:**
- Consumes: [用到的前置任务产出——精确签名]
- Produces: [后续任务依赖的产出——精确函数名、参数与返回类型。执行者只看得到自己这一份任务；这块是他们得知相邻任务所用名字与类型的唯一途径。]

- [ ] **Step 1: 写失败测试**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **Step 2: 跑测试确认失败**

Run: `pytest tests/path/test.py::test_name -v`
Expected: FAIL, "function not defined"

- [ ] **Step 3: 最小实现**

```python
def function(input):
    return expected
```

- [ ] **Step 4: 跑测试确认通过**

Run: `pytest tests/path/test.py::test_name -v`
Expected: PASS

- [ ] **Step 5: Commit**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

## 禁止占位符：借口 vs 现实

占位符是**计划失败**，不是风格瑕疵——出现即重写：

| 常见借口 | 现实 |
|---|---|
| "TBD / TODO / 稍后再补" | 执行者没有上下文替你补——这正是他们手里只有计划的原因。 |
| "加上适当的错误处理 / 校验 / 处理边界情况" | "适当"由谁定？写出具体代码。 |
| "为上面写测试"（不带测试代码） | 贴出完整测试，不要描述测试。 |
| "同 Task N" | 执行者可能乱序读任务——重复贴代码。 |
| 只说做什么，不示范怎么做 | 代码步骤必须带代码块，验证步骤必须带命令与预期输出。 |
| 引用任何任务都未定义的类型/函数/方法 | 编造的名字在执行时就是编译错误。 |

## 红线自查

写完整个计划后，以新鲜视角对照规格自查（自己跑这份清单，不派子代理/后台代理（若有）代劳）：

1. **规格覆盖**：规格每节/每条需求都能指向一个实现它的任务？有缺口就补任务。
2. **占位符扫描**：全文搜上表红旗模式，发现即修复。
3. **类型一致性**：后续任务用到的类型、签名、属性名与前面任务定义的一致？Task 3 叫 `clearLayers()`、Task 7 叫 `clearFullLayers()` 就是 bug。
4. **Review Focus 落实**：规格隐含的每类输入/失效模式都有任务的测试踩到它？前五条未覆盖者写入 Review Focus，各配测试挂到 owning task。该节为空 = "查过、没有"，不是"没查"。

发现问题就地修复、不必重审；缺任务就加任务。

## 移交执行

1. 保存并自查后，请用户审阅计划；确认前不进入实现。
2. 用户未指定执行方式时，推荐其一并附一句来自计划的依据（任务间接口依赖多少、任务数量、出错代价）：
   - **子代理逐任务（若有子代理/后台代理）**：每任务派新代理实现、新代理评审通过后才进下一个，最后整分支评审。最彻底，每任务上下文成本最高。
   - **本会话逐任务**：自己按序执行全部任务，最后由全新评审视角整分支评审一次。最快最省；设计已由计划承载，独立性可接受。
3. 执行交 dev-executing-plans；测试纪律见 dev-tdd；需要隔离工作区时见 dev-git-worktrees（执行时创建）。
