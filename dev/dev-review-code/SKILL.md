# dev-review-code：代码评审（双轴 + 严重分级）

评审一段 diff / 一个分支 / 一个 PR：先问「做的是不是要它做的事」（**Spec 轴**），再问「做得符不符合规矩」（**Standards 轴**），发现按 CRITICAL / HIGH / MEDIUM / LOW 分级报告。

## 为什么两轴分开

一个改动可以过一轴、挂另一轴：处处合规却做错了东西（Standards 过、Spec 挂）；正中需求却破坏项目约定（Spec 过、Standards 挂）。两轴分开报告，防止一个轴的好成绩掩盖另一个轴的问题。

## 第一步：锁定范围

- 用户给了 diff → 审 diff；给了文件/目录 → 通读整体审；说「review since X / 评审这个分支」→ 固定点 = X。
- 固定点：commit SHA、分支名、tag、`main`、`HEAD~5` 都行。没给就问，不要猜。常见默认是未提交改动。
- 先验证固定点可解析、diff 非空——坏引用和空 diff 在这一步就该失败，不要拖进两轴评审里。

## 第二步：找需求来源（Spec 轴的对照物）

按顺序找：

1. 提交信息里的 issue 引用（`#123`、`Closes #45`），到项目使用的任务追踪系统里取原文；
2. 用户给过的路径，或粘贴过的需求文本；
3. `docs/`、`specs/` 下与分支名/功能名匹配的规格文件（dev-spec / dev-writing-plans 的产物常在这里）；
4. 都没有 → 问用户；确认没有 → Spec 轴记「无需求可对照」并跳过，报告里必须写明。

**判定基准**：规格是愿景不是穷举。规格没写的场景，按「一个正常使用者会怎么期待」判定——使用者的合理期待就是需求，规格沉默不等于许可。发现「问题出在规格/计划本身而非实现」时，单独说出来，不要算在实现头上。

## 第三步：收集 Standards 轴的对照物

1. 仓库自己声明的规范（`CODING_STANDARDS.md`、`CONTRIBUTING.md` 等），有就列成清单；
2. 仓库没覆盖的，用下面的通用底线兜底。

两条元规则：**仓库规范压过通用底线**——仓库明文认可的写法，不再按底线报；**工具已强制的跳过**——formatter / linter 管了的事，不重复报。

## Standards 通用底线（速查表）

按代码实际涉及的部分取用：纯前端跳过 SQL 行，无循环取数跳过 N+1。用户只要「快速看一眼」→ 只扫 🔴 两行；用户要「完整评审 / 全面审计 / 上线把关」→ 全表过完。

| 级别 | 类别 | 模式 | 判定 |
|---|---|---|---|
| 🔴 CRITICAL | 安全 | f-string / `+` 拼接 SQL | SQL 注入，改参数化查询 |
| 🔴 CRITICAL | 安全 | 用户输入进 `innerHTML` / 模板插值 | XSS，改 `textContent` 或先 sanitize |
| 🔴 CRITICAL | 安全 | 硬编码密钥、缺失鉴权、越权 | 阻塞合并，立即修 |
| 🟠 HIGH | 性能 | 循环内逐条查询 / 取关联数据 | N+1，改 JOIN / eager load / 批量 IN |
| 🟠 HIGH | 正确性 | 裸 `except:`、`except Exception: pass` 类吞错 | 改具体异常 + 记日志，或带上下文重抛 |
| 🟠 HIGH | 正确性 | 竞态、边界 / 错误路径缺失、数据丢失风险 | 合并前修复 |
| 🟡 MEDIUM | 可维护性 | `x`、`tmp`、`data` 等无意义命名 | 改成意图明确的名称 |
| 🟡 MEDIUM | 可维护性 | 函数签名缺类型标注（在有类型系统的语言里） | 补标注 |
| ⚪ LOW | 风格 | 纯风格偏好、微小优化 | 可选 |

规则是启发式，不是枚举器：只报真实命中模式的问题，不把一切差异拔高成 CRITICAL。表未覆盖但影响明显的问题（竞态、缺失鉴权等）也报——就近归级，并在 Issue 里说明依据。测试缺失不算缺陷级别，但在结论里提示是否补测试覆盖新代码的错误路径。

**坏味道速查**（🟡 判断题：标「疑似」不标「违规」；仓库规范认可的，suppress）：

| 坏味道 | 信号 → 方向 |
|---|---|
| 神秘命名 | 名字说不出它做什么/装什么 → 改名；想不出诚实的名字，说明设计浑了 |
| 重复代码 | 同形逻辑出现多处 → 提取共享，两处调用 |
| 特性依恋 | 方法总在够别的对象的数据 → 把方法挪到它依恋的数据上 |
| 数据泥团 | 几个字段/参数总是结伴出现 → 捆成一个类型传递 |
| 基本类型偏执 | 用原始值顶替领域概念 → 给概念立个小类型 |
| 重复分支 | 同一类型上的同款 switch / if 级联反复出现 → 多态或共享映射 |
| 霰弹式修改 | 一个逻辑改动散落整个 diff → 聚到同一模块 |
| 投机泛化 | 为规格没提的需求加的抽象/参数/钩子 → 删掉，等真需求出现再加 |

## 第四步：跑两轴（能力探测）

**有子代理 / 后台代理工具 → 并行模式**：两轴各派一个代理，互不知晓对方存在，各自回报。diff 大时分开发跑还能防止一轴的发现污染另一轴的判断。

- **Spec 代理任务书**：diff 范围 + 提交列表 + 需求原文。报告 (a) 需求要求但缺失/半成品的行为 (b) diff 里没被要求的行为（范围蔓延）(c) 看似实现但与需求不符之处。每条引用需求原句。
- **Standards 代理任务书**：diff 范围 + 提交列表 + 仓库规范清单 + 本文件上面的速查表与坏味道表**全文**（它没别的途径看到）。按文件/hunk 报告命中项，引用规则出处，区分硬违规与判断题。
- 两个代理都是**只读评审**：不碰工作区、HEAD、分支状态；要看别的版本去临时目录看。代理内部不再派代理。
- 汇总时不合并、不跨轴重排：两轴报告分列呈现，各轴内部指出最重一条即可，不评「全局最严重」。

**没有子代理工具 → 顺序模式**：同一会话先 Spec 后 Standards。过完 Spec 清单后明确换轴——Spec 的发现放在一边，用 Standards 清单从头再过一遍 diff，不顺路夹带。

## 第五步：输出报告

每条发现必带 `文件:行号` 和级别；说明文字用中文，代码、路径、标识符、报错保持原文；没有真实命中就不要硬凑。

```markdown
## 做得好的
- <具体、简短的 1-3 条>（准确的肯定，让后面的批评可信）

## Spec 轴（对照 <需求来源>）
- <缺失/半成品 | 范围蔓延 | 实现有误，每条带 文件:行号 + 需求原句>

## Standards 轴
### CRITICAL: <一句话问题名>
**File:** `path:line`
**Issue:** <问题与利用方式/后果，一句话>
**Fix:** <可直接落地的修法，能贴修复代码就贴>

## 结论：能不能合
- Spec 轴 n 条；Standards 轴：🔴 n / 🟠 n / 🟡 n / ⚪ n
- **判定**：有 🔴 → 不能合，立即修；无 🔴 有 🟠 → 修完再合；只剩 🟡/⚪ → 可合，留 TODO
```

## 常见借口 vs 现实

| 借口 | 现实 |
|---|---|
| 「用户只要快速看一眼，Spec 轴跳过吧」 | 方向错了，代码再干净也是白干。「快速看一眼」至少要确认改动声称要做的事真做了，否则「没问题」三个字是骗人。 |
| 「改动很小，不用找需求来源」 | 越小的改动越容易悄悄偏离意图；花两分钟找 issue 引用，避免合错东西。 |
| 「不确定算不算问题，标 CRITICAL 稳妥」 | 拔高级别是把判断成本甩给用户；不确定就降级或核实。CRITICAL 只留给安全与数据丢失。 |
| 「这段看起来能跑就行」 | 「看起来能跑」不是评审结论；没确认测试与调用方之前，不许说「没问题」。 |

## 红线自查（报告发出前过一遍）

- [ ] 固定点已验证可解析、diff 非空？
- [ ] Spec 轴跑过，或明确记录了「无需求可对照」？
- [ ] 每条发现带 `文件:行号`？Spec 轴发现带了需求原句？
- [ ] 级别按实际影响定，没有把风格偏好拔高成 CRITICAL？
- [ ] 工具已强制的（formatter / lint）没有重复报？
- [ ] 全程只读，没碰工作区 / HEAD / 分支状态？
- [ ] 给出了明确的「能不能合」结论，没有「看起来还行」式含糊话？
- [ ] 没有对没读过的代码发表意见？

## 常见错误

- 只看 diff 不看需求 → 代码漂亮但答非所问
- 把 Standards 发现混进 Spec 报告（或反之）
- 汇总时把两轴揉成一个榜单重排
- 只给「改进错误处理」这类空话，不给位置和具体修法
- 硬凑发现：没命中规则也要挤几条显得认真
