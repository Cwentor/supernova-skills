# dev-request-review：发起代码评审

活干完 ≠ 活干对了。评审要趁问题还没级联放大时发起，评审者拿到的是**精心准备的上下文**——绝不是你的会话历史。核心原则：早评审、勤评审。

## 什么时候请求评审

| 场景 | 强度 |
|---|---|
| 完成一个大功能 | 必须 |
| 准备合并进主干 | 必须 |
| 多任务计划里完成一个独立任务 | 必须——每个任务完成即评，不等全部做完（见 dev-executing-plans 的检查点） |
| 卡住了 | 可选但高价值——新视角常常直接破局 |
| 大重构动工前 | 可选——先给现状拍基线 |
| 修完一个复杂 bug | 可选 |

## 请求怎么写（评审质量 = 上下文质量）

六个要素，一个都不靠会话历史：

1. **范围（固定点）**：从哪到哪。`git diff <base>...<head>`；base 用 merge-base（`git merge-base origin/main HEAD`）或上一个任务的完成点。
2. **做了什么**：一两句概括本次改动。
3. **对照需求**：计划文件路径、票据文本或需求原文——评审者要拿它判断「做的是不是要你做的」。
4. **重点关注**：你自己最没把握的 1-3 处（错误处理？边界？并发？），点名 `文件:行号`。
5. **只读约束**：告诉评审者不许改动工作区、HEAD、分支状态。
6. **要结论**：要求明确回答「能不能合 / 能不能继续」，不许含糊。

```markdown
请评审以下改动（只读评审，不要改任何文件 / 分支状态）：
- 范围：<base SHA 或分支> … <head>
- 做了什么：<一两句>
- 对照需求：<计划 / 票据路径，或需求原文>
- 重点关注：<你最担心的 1-3 处，文件:行号>
- 产出：做得好的 / 按严重级别列发现（每条带 文件:行号）/ 明确结论（能合 | 修完能合 | 不能合）
```

## 派给谁（能力探测）

- **有子代理 / 后台代理工具**：把上面的请求原文派给一个评审代理，让它按 dev-review-code 的双轴口径执行。diff 的阅读消耗在它的上下文里，你只拿回发现清单——保住你自己继续推进工作所需的上下文。
- **没有**：请人类同事或用户评审；或在另一个干净会话里评——总之「写代码的上下文」和「评审的上下文」最好不是同一份。实在只有自己：把请求模板存成文件，隔一段时间 / 换个任务后再按清单冷读自己的 diff。

## 拿到回评后

- CRITICAL 立即修；HIGH 继续推进前修掉；MEDIUM / LOW 记下来延后。分级名目不一致时按含义映射。
- 认为评审者说错了 → 用技术理由和证据反驳，别硬顶也别照单全收（逐条处理见 dev-receive-feedback）。

## 最佳示例

完成「任务 2：验证函数」后，发起评审：

```bash
BASE_SHA=$(git rev-parse HEAD~1)   # 或 git merge-base origin/main HEAD
HEAD_SHA=$(git rev-parse HEAD)
```

请求：范围 a7981ec…3df7661；做了什么：新增 `verifyIndex()` 和 `repairIndex()`，4 种问题类型；对照需求：计划文件里的任务 2；重点关注：`repairIndex()` 的错误路径。

回评：做得好——结构干净、测试真实；HIGH——缺进度提示；LOW——魔数 `100`。结论：修完可继续。
→ 补上进度提示，继续任务 3。

## 常见借口 vs 现实

| 借口 | 现实 |
|---|---|
| 「我自己把 diff 再读一遍就行」 | 你刚写完它，带着写作时的全部偏见；需要的是没参与写作的眼睛。有子代理工具时，重读 diff 还会烧掉你推进工作所需的上下文。 |
| 「评审者需要我的整个会话历史才能理解改动」 | 交精制的上下文，永远不倒会话历史。历史会让评审者去考古你的思路，而不是看工作成果本身。 |
| 「改动很简单，跳过评审吧」 | 「简单」是改动的属性，不是跳过检查的理由；恰恰是简单改动让人在「能不能合」上翻车。 |
| 「等全部做完一起评审省事」 | 问题会级联：任务 3 建在任务 2 的错误上，返工翻倍。每完成一个可评审单元就评一次。 |

## 红线自查

发出请求前：

- [ ] 范围固定点写清楚了，且能解析？
- [ ] 给了对照需求（不只是 diff）？
- [ ] 点名了自己最担心的点？
- [ ] 写明只读评审？
- [ ] 明确要求了结论？

拿到回评后：

- [ ] 没有以「它很简单」为由跳过过评审？
- [ ] CRITICAL 没被无视？HIGH 没被拖过？
- [ ] 不同意的技术意见在用证据反驳，而不是嘴硬或盲从？

## 常见错误

- 请求里只给 diff 范围、不给需求 → 评审者只能评「代码漂不漂亮」，评不了「对不对」
- 把会话历史倒给评审者
- 不给重点关注 → 评审者平均用力，你最担心的地方没被多看一眼
- base 没固定（「从头到 HEAD」），范围漂移
- 拿到回评只看结论，不逐条看具体发现

**配合使用：** dev-review-code（评审本身怎么执行）、dev-receive-feedback（拿到回评后逐条怎么处理）、dev-executing-plans（任务检查点）
