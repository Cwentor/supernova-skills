# 系统化调试

## 概述

**核心原则：** 永远先找到根因，再动手修复。修症状就是失败。

**违反流程的字面，就是违反调试的精神。**

## 铁律

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

没完成阶段一，一个修复方案都不许提。

## 何时使用

任何技术问题：测试失败、生产 Bug、意外行为、构建失败、集成问题。

**典型触发场景：** 硬 bug（常规思路打不穿）、性能回归（「变慢了」）、间歇性失败（时好时坏、flaky）。

**恰恰在这些时刻最想跳过流程，越是这样越要走流程：**
- 时间压力大（紧急让人想瞎猜）
- 「就一个小修复，显而易见」
- 已经试过几个修复都没用
- 自己也没完全理解问题

简单 bug 也有根因；赶时间只会保证返工；系统化比乱试快。

## 阶段一：紧反馈回路——复现并最小化

**这一步就是本技能的全部**，其余步骤都在消费它：一条命令（一个测试、一条 curl、一个脚本）就能对**这个** bug 变红——断言用户描述的确切症状，而不是「没崩就没事」——修好它就转绿。没有这个回路，盯多久代码都救不了你。

构造方式，按序尝试：

1. 够得着 bug 的失败测试（单元/集成/E2E 均可）
2. 对运行中服务的 curl / HTTP 脚本
3. 带固定输入的 CLI 调用，stdout 对比已知正确的快照
4. 无头浏览器脚本，断言 DOM/console/network
5. 回放真实抓包 / 事件日志
6. 一次性搭最小子系统（单个服务 + mock 依赖），一次函数调用触发 bug 路径
7. 「有时输出错误」类 bug：跑 1000 个随机输入找失败模式
8. bug 出现在两个已知状态（提交、数据集、版本）之间：自动化「起状态 X → 检查 → 重复」做二分
9. 同一输入走新旧版本（或两套配置），diff 输出

**收紧回路**：更快（缓存 setup、砍无关初始化）、信号更尖（断言具体症状）、更确定（钉死时间、固定随机种子、隔离文件系统与网络）。30 秒的 flaky 回路几乎等于没有回路；2 秒的确定性回路是调试超能力。

**间歇性 bug：** 目标不是干净复现，而是**提高复现率**——循环触发 100 次、加压、收窄时间窗、注入等待。50% 复现的 bug 可调试，1% 的不可调试。

**真造不出回路：** 明说并列出已试方案，向用户要 (a) 能复现的环境访问、(b) 脱敏后的抓取物（HAR、日志、带时间戳的录屏）、(c) 加临时生产插桩的许可。**没有回路不许进入假设阶段。**

回路红了之后继续阶段一：

- **完整读错误信息**：stack trace 逐行读完，记下行号、文件、错误码；不许略过 warning
- **查最近改动**：diff、新依赖、配置变化、环境差异
- **最小化**：回路红着的前提下，逐项裁剪输入/调用方/配置/步骤，一次删一项再跑，直到「每个留下的元素都承重」（去掉任一项回路就转绿）。最小复现收窄假设空间，日后直接变成回归测试
- **多组件系统**：提出修复前，先在组件边界记录进出数据与配置传播，跑一次让证据指出**断在哪一层**：

```bash
# 每层打印该层可见的关键数据与环境变量，跑一次定位断点
echo "=== build 阶段可见: ==="
env | grep "$KEY" || echo "$KEY not in environment"
```

  让证据说话（秘密传到了 CI ✓、CI 没传给构建 ✗），再只深入那一层
- **数据流回溯**：坏值从哪来？谁用坏值调用了它？沿调用栈向上追到源头；**在源头修，不在症状处修**

## 阶段二：模式对照

- 在同一代码库找**能工作的相似实现**；列出它与损坏版本之间的**每一处**差异，再小也不许说「这不可能有影响」
- 参考某个模式/规范实现时，**完整读完**，不许略读后「改编」——半懂就是埋 bug
- 理解依赖：需要哪些组件、配置、环境，做了哪些假设

## 阶段三：假设与最小验证

- 先生成 **3–5 个排好序的可证伪假设**（单假设会锚定在第一个似是而非的念头上）。格式：「若 X 是根因，则改动 Y 会让 bug 消失/恶化」；说不出预测的假设是感觉，扔掉或磨尖
- 每个探针对应一个具体预测；**一次只改一个变量**；假设不成立→换**新**假设，不许在失败修复上再叠修复
- 工具优先级：调试器/REPL 断点 > 定点日志（放在能区分假设的边界上）；禁止「全量打日志再 grep」
- 给每条调试日志打唯一前缀（如 `[DEBUG-a4f2]`），收尾一次 grep 清干净
- **性能回归分支：** 日志通常是错工具。先建基线测量（计时、profiler、查询计划），再二分。**测量先于修复**
- 不懂就说不懂，去问、去查，不许装懂

## 阶段四：修复与验证

1. **先写回归测试**：把最小复现变成失败测试，看它红（红绿循环见 dev-tdd）。没有正确的接缝（测试无法在真实调用场景下触发该 bug）时，记下「无接缝」——这本身就是一个发现：架构挡住了回归防护，标记出来
2. **单一修复**：只改根因那一处，一次一个改动。拒绝「顺手优化」和捆绑重构
3. **验证**：回归测试转绿；用阶段一的回路重跑**原始未最小化**场景，确认用户症状消失；整个套件仍全绿
4. **修复不奏效**：数一数已试方案数。少于 3 个 → 带着新信息回阶段一；**3 个及以上 → 停下质疑架构**——每次修复都在别处引出新问题、要大重构才能落地，说明当前模式从根本上错了。与用户讨论（可配合 dev-improve-architecture），不许再试第 4 个

## 收尾清理（宣布搞定前必做）

- [ ] 原始复现不再复现（重跑阶段一回路）
- [ ] 回归测试通过（或已记录「无正确接缝」）
- [ ] 全部 `[DEBUG-...]` 插桩已移除（grep 前缀确认）
- [ ] 一次性脚本已删除，或移入明确标记的调试目录
- [ ] 证实的根因写进了提交说明/PR 描述，让下一个调试者直接受益
- [ ] 展示命令与输出前已抹掉密钥（替换为 `<REDACTED>`）

## 当流程显示「没有根因」

系统性调查后确认问题真出在环境/时序/外部：记录已调查项，实现恰当处理（重试、超时、清晰报错），加监控留证。**但 95% 的「查不到根因」是调查不彻底。**

## 常见借口 vs 现实

| 借口 | 现实 |
|------|------|
| 「问题很简单，不用走流程」 | 简单 bug 也有根因；流程对简单 bug 很快 |
| 「紧急，没时间走流程」 | 系统化调试比「猜-改-跑」打转快得多 |
| 「先试一下这个，回头再查」 | 第一个修复定调；从一开始就做对 |
| 「确认修复有效后我再补测试」 | 没测试的修复守不住；先写测试它才能证明自己 |
| 「一次改多处省时间」 | 无法隔离哪个改动生效，还会引入新 bug |
| 「参考实现太长，我改编一下」 | 半懂就是埋 bug；完整读完 |
| 「我看到问题了，直接改」 | 看到症状 ≠ 理解根因 |
| 「再试一次修复」（已失败 2 次以上） | 3 次失败 = 架构问题；质疑模式，别再修 |
| 「读代码建立理论更快」 | 没有红色回路前的一切理论都是猜；这正是本技能要防的失败 |

## 红线自查

抓住自己在想以下任何一条：停下，回阶段一：

- 「先快速修一下，回头再查」
- 「改改 X 试试能不能好」
- 「多改几处，跑一遍测试看看」
- 「跳过测试，我手动验证」
- 「八成是 X，我直接修它」
- 「我没完全懂，但这也许管用」
- 还没建回路就开始读代码想理论
- 还没追踪数据流就列出「问题主要是：」并附修复方案
- 第 3 个修复方案已经在路上

## 与其他技能的关系

- 回归测试按 dev-tdd 的红绿循环写，修复必带回归测试
- 宣称「修好了」之前，按 dev-verification 实际运行验证并引用真实输出
- 3 次修复失败后的问题是架构问题 → dev-improve-architecture
