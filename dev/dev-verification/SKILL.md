# 完成前验证

## 概述

**核心原则：** 证据先于断言，永远。

**违反规则的字面，就是违反规则的精神。**

## 铁律

```
NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE
```

本轮对话里没运行过验证命令，就不能宣称它通过。

## 门函数

准备宣称任何状态或表达满意时，依次走完：

1. **识别**：什么命令能证明这个宣称？
2. **运行**：完整、新鲜地执行它——不是引用上一次的输出
3. **阅读**：读完整输出，看退出码，数失败数
4. **核对**：输出确认了宣称吗？
   - 否 → 陈述实际状态，附证据
   - 是 → 带着证据宣称
5. 这之后才允许说「通过/完成」

跳过任何一步 = 在撒谎，不是在验证。

## 每种宣称需要什么证据

| 宣称 | 需要 | 不够 |
|------|------|------|
| 「测试通过」 | 测试命令输出：0 失败 | 上一次的运行、「应该会过」 |
| 「Linter 干净」 | Linter 输出：0 error | 只查了部分、外推 |
| 「构建成功」 | 构建命令 exit 0 | Linter 过了、日志看着顺眼 |
| 「Bug 修好了」 | 针对原始症状的验证通过 | 改了代码、想当然 |
| 「回归测试有效」 | 红绿循环完整走过 | 测试只跑过一次绿的 |
| 「子代理/后台代理完成了」 | 亲自查看工作目录的实际改动 | 代理报告「成功」 |
| 「需求满足」 | 对照计划逐条核对 | 测试通过 |

## 关键模式

**测试：**
- ✅ [运行测试命令] [引用输出：34/34 通过] 「全部测试通过」
- ❌ 「现在应该过了」「看着是对的」

**回归测试（红绿验证，见 dev-tdd）：**
- ✅ 写 → 跑（过）→ 还原修复 → 跑（必须失败）→ 恢复修复 → 跑（过）
- ❌ 「我写了回归测试」（没做过红绿验证）

**子代理/后台代理：**
- ✅ 代理报告成功 → 亲自查实际改动 → 验证内容 → 按实际状态报告
- ❌ 直接转述代理的「成功」

**需求：**
- ✅ 重读计划/规格 → 列清单 → 逐项核对 → 报告缺口或完成
- ❌ 「测试都过了，这一阶段就算完了」

## 何时适用

以下时刻一律先过门函数：

- 任何「完成/搞定/通过/修好」的说法，包括原话、转述、同义说法、暗示成功的表达
- 任何满意的表达（「成了！」「完美！」）
- 提交、创建 PR、交付、转入下一任务之前
- 汇报子代理/后台代理的工作成果之前

规则不因措辞不同而失效：精神高于字面。

## 常见借口 vs 现实

| 借口 | 现实 |
|------|------|
| 「现在应该可以了」 | 去运行验证命令 |
| 「我很有把握」 | 把握 ≠ 证据 |
| 「就这一次」 | 没有例外 |
| 「Linter 过了」 | Linter ≠ 编译器，更 ≠ 测试 |
| 「代理说成功了」 | 独立验证过再说 |
| 「我累了，想收尾」 | 疲惫不是借口 |
| 「查了一部分，够了」 | 部分验证什么也证明不了 |
| 「换个说法规则就不适用」 | 精神高于字面 |

## 红线自查

- 用到「应该」「大概」「看起来」
- 还没验证就表达满意（「成了！」「搞定！」）
- 没跑验证就要提交/交付
- 信任代理的成功报告而不核实
- 依赖部分验证
- 想着「就这一次」
- 累了，只想快点结束
- 任何暗示成功但没运行过验证的措辞

出现任何一条：停下，先运行验证命令，引用真实输出，再说话。
