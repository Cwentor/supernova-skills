# dev-prototype

原型是**为回答一个设计问题而写的一次性代码**。问题决定原型的形态；原型结束时，必须给出这个问题明确的答案。

「一次性」约束的是**写法**，不是承诺销毁：代码按可丢弃标准写——无测试、无抽象、错误处理只到能跑——但**被验证的结论必须吸收进真实实现**；原型本体则归档到独立分支或目录，作为可回溯的一手资料。

## 第一步：写下问题

先写下要回答的问题再写代码，一段话放在原型开头可见处（不只是注释）：「这个状态模型能否处理 X 之后再 Y？」「设置页应该长什么样？」。答错问题的原型是纯浪费；问题写显式了才能事后核验。

两类问题，两种形态：

- **逻辑 / 状态对不对** → 逻辑原型（分支 A）
- **界面该长什么样** → 界面原型（分支 B）

问题含糊且用户不在场时：按上下文猜（后端模块 → 逻辑；页面 / 组件 → 界面），并在原型开头声明这个假设。

## 分支 A：逻辑原型

回答的问题是业务规则、状态迁移、数据形状是否成立。形态：**单个自包含 HTML 文件**——双击即开、可随手转发，能交给非开发者（设计师、业务方）亲手把玩。纸上合理的状态模型，推进真实用例才会露馅，露馅正是原型的产出。

1. **把被拷问的逻辑隔离成纯模块**：与页面无关的独立块（一个 `<script>` 或独立文件），按问题选形状——离散事件选纯 reducer `(state, action) => state`；「当前哪些动作合法」本身是问题一部分时选显式状态机；无隐含当前状态选一组纯函数；确需持有内部状态选方法面清晰的类。页面是薄壳：只调用模块，绝不反向依赖（不碰 DOM、不碰 `document`）。这是原型中唯一将来可整体搬进真实代码的部分。
2. **页面按非开发者习惯组织**，自上而下：标题与一句话问题；完整当前状态面板（带标签的字段，不是裸 JSON），每次动作后重渲染并高亮变化；每个动作一个自由把玩按钮；再加一组引导场景页签——每个场景一段白话描述加按序可点的真按钮，从固定初始状态开始。场景专挑纸上难推理的：快乐路径、刁钻边界、尝试一件应该被禁止的事。
3. **全用领域语言**：按钮和状态读起来像业务，不像代码。

## 分支 B：界面原型

回答的问题是这个界面该长什么样。形态：**同一页面挂若干结构迥异的变体**，一个浮动切换条循环切换，用户翻着比较、整块选或拼装（「要 B 的页头配 C 的侧栏」才是真实需求）。

1. 默认 3 个变体，上限 5 个。变体必须**结构性不同**：布局、信息层级、主操作各异——只换颜色或文案是壁纸不是原型；共享页头可以，共享整页布局则扼杀差异。只读即可，确需写操作就指向 stub：问题不是「后端能不能用」。
2. **优先寄生在既有页面上**：真实页头、真实数据、真实密度——空路由里每个变体看着都不错，会掩盖设计问题。在既有路由上用 `?variant=` 切换、只换渲染子树，数据获取与鉴权保留原样。新造独立路由是下策，仅当确实无处安放才用，且遵循项目既有路由约定、路径带 `prototype` 字样。
3. 切换条固定于底部居中：左右箭头循环切换、显示当前变体名；状态同步进 URL 参数（可分享、刷新可恢复）；视觉上明显不属于被评估的设计；生产构建下不出现。示意（按项目框架适配）：

```tsx
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A', 'B', 'C']} current={variant} />
  </>
);
```

## 通用纪律

1. **隔离**：原型放独立目录（如 `prototypes/`）或专用分支，命名让人一眼看出是原型，不污染主工作区；只有被验证的结论可以进主线。UI 变体确需寄生既有路由时，答案落地后立即把原型本体移出主线。
2. **一键可跑**：界面原型是任务器里的一条命令，逻辑原型是双击即开的单文件；启动不需要思考。
3. **默认无持久化**：状态放内存；问题确涉及持久化时，也只打临时数据库或名字带 `PROTOTYPE, wipe me` 字样的本地文件。
4. **跳过打磨**：无测试、无多余错误处理、无抽象；目的是快速学到东西。
5. **随时暴露状态**：每次动作或变体切换后打印 / 渲染完整相关状态，让用户看见变化。
6. **结束即收档**：答案（结论 + 它了结的问题）记进任务单或提交说明；被验证的逻辑模块搬进真实代码，胜出变体在正式代码里**重写**；原型本体移到一次性分支归档。

## 常见借口 vs 现实

| 借口 | 现实 |
|---|---|
| 「原型写得挺好，直接转正吧」 | 原型按可丢弃标准写：无测试、无错误处理。转正 = 在真实实现里重写，只吸收结论。 |
| 「顺手给原型加几个测试」 | 需要测试的原型就不再是原型；测试拖慢的是回答问题的速度。 |
| 「把原型写完整点，以后直接用」 | 原型只回答一个问题，从不为复用而设计。「以后用得上」是发散的开始。 |
| 「问题很清楚，不用写下来」 | 没写下问题就无法核验答没答对题；含糊时你根本不知道在验证什么。 |
| 「就在生产代码旁边改一改试试」 | 可丢弃标准的代码混进主线就是技术债；隔离是原型的第一属性。 |

## 红线自查

- 没写下要回答的问题就开写 → 停，先写问题
- 纯逻辑模块里出现 DOM、`document` 或按钮回调 → 不再可搬运，剥离出来
- 变体之间只差颜色或文案 → 重做，要结构级差异
- 原型接上真实数据库或生产数据 → 断开，用内存态或 stub
- 原型文件留在主分支，或切换条出现在生产构建 → 移到一次性分支、加构建开关
- 问题已有答案却没记录 → 把结论与问题一起写进任务单 / 提交说明

命中任何一条都意味着原型正在失去它唯一的优势：快。停下修正再继续。

**配合使用：** dev-brainstorming（原型之前先把要验证的问题收敛清楚）
