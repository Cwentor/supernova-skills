# dev-receive-feedback：接收评审意见

代码评审要的是技术评估，不是情绪表演。核心原则：**先验证，再实现。先问清，再假设。技术正确高于社交舒服。**

## 响应序列

1. **读完**：整份意见读完再反应，中途不插话、不提前反驳。
2. **复述**：用自己的话重述每条要求；复述不出来 = 没理解。
3. **核实**：逐条对照代码现状——这个说法在这套代码里成立吗？
4. **评估**：对这个代码库、这个技术栈，这条建议技术上站得住吗？
5. **回应**：技术性确认，或有理有据的反驳。
6. **实现**：一次一条，每条改完单独验证。

## 禁止的回应

- ❌「你说得太对了！」/ "You're absolutely right!"（表演性同意）
- ❌「好观点！」「多谢提醒！」（任何感谢 / 夸奖句式）
- ❌「我这就去改」（还没核实就动手）

替代：复述技术要求本身，或直接开始干活——修好的代码就是最好的回应。发现自己正要写「谢谢」：删掉，改成陈述修复内容。

## 意见不清晰时

任何一条不清楚 → **全部先停**，先把不清楚的问清楚，再动任何一条。原因：意见之间可能相关，半懂状态下动手实现是在制造新 bug。改了 4 条懂的不算进度，问清 2 条不懂的才算开始。

## 按来源分级信任

| 来源 | 信任度 | 动作 |
|---|---|---|
| 你的用户 / 项目负责人 | 高 | 理解后即可实现；范围不清照样要问 |
| 外部评审者 / 陌生会话 | 存疑 | 实现前先过下面五问 |

**外部意见的五问**：

1. 对这个代码库技术成立吗？
2. 会不会弄坏现有功能？
3. 现有实现当初为什么这么写——有历史 / 兼容性原因吗？
4. 在所有目标平台 / 版本上成立吗？
5. 评审者掌握全部上下文吗？

核实不了就直说：「没有 X 我核实不了这条。要我调查、去问、还是先跳过？」外部意见与你用户先前的决策冲突 → 停，先找你的用户对齐。对外部意见的纪律：审慎对待、仔细核查——不是一概抗拒，也不是一概照办。

## YAGNI 检查

评审者要求「把这个功能实现完整 / 规范化」时，先在代码库里搜这个功能到底有没有人用：

- 没有任何调用方 → 反问：「这个入口没有任何调用方。是删掉（YAGNI），还是有我没看到的用途？」
- 确实有人用 → 再好好实现。你和评审者都服务于项目：不需要的功能，就不要加。

## 什么时候必须反驳

- 建议会弄坏现有功能
- 评审者缺上下文（不知道某段代码的存在理由）
- 违反 YAGNI（功能根本没人用）
- 对这个技术栈技术上不成立
- 存在历史 / 兼容性原因
- 与你的用户已定的架构决策冲突

**怎么反驳**：用技术理由，不防御；引用能跑的测试和代码作证；问具体问题；涉及架构的把你的用户拉进来。不敢反驳时，把这份紧张说出来，然后把你看到的问题原样讲给你的用户——诚实比舒服值钱。

反驳错了就认，一句事实陈述然后继续干活：「我查了 X，它确实会 Y。你是对的，我当初理解错了，因为 Z。现在改。」不写长道歉、不为反驳辩护、不过度解释。

## 实现顺序（多条意见）

1. 先澄清所有不清楚的；
2. 再按 阻断性（会坏 / 安全）→ 简单修（错字 / 导入）→ 复杂修（重构 / 逻辑）的顺序实现；
3. 每条单独测试，改完确认无回归。

## 最佳示例

```
评审者：「把遗留代码删掉」

❌「你说得太对了！我这就删……」

✅「核实中……构建目标是 10.15+，这个 API 要 13+。遗留分支是给旧版本兜底的。
    当前实现的 bundle ID 确实错了——修 bundle ID，还是放弃 13 以前的支持？二选一。」
```

先验证、再表态、把决策点交回去——而不是先表忠心再动代码。

## 常见借口 vs 现实

| 借口 | 现实 |
|---|---|
| 「对方是专家，直接照做省事」 | 专家也会看走眼；盲改的返工成本高于核实成本。 |
| 「先改了再说，边改边理解」 | 意见之间可能相关；半懂状态动手是在制造新 bug。 |
| 「反驳不礼貌」 | 用技术理由反驳是职业行为，弄坏代码才是失职；实在开不了口，就把问题如实告诉你的用户。 |
| 「感谢一句是基本礼貌」 | 修复本身和准确复述就是回应；感谢句式是噪音，还挤掉真正的信息。 |
| 「核实不了，大概没事，先干了」 | 核实不了就明说、要方向；硬干是拿代码赌运气。 |

## 常见错误

| 错误 | 修正 |
|---|---|
| 表演性同意 | 陈述要求本身，或直接动手 |
| 盲目实现 | 先对照代码现状核实 |
| 一批全改、不逐条验证 | 一次一条，每条测 |
| 默认评审者是对的 | 先查会不会弄坏东西 |
| 该反驳不反驳 | 技术正确高于舒服 |
| 部分实现（有几条没懂就动手） | 先全部澄清再实现 |
| 核实不了还硬干 | 说出局限，要方向 |

## 红线自查

动手前：

- [ ] 每条意见都能用自己的话复述？
- [ ] 没有任何一条处于「拿不准但先改了」状态？
- [ ] 外部意见过了五问？
- [ ] 「规范化 / 实现完整」类要求做过 YAGNI 搜索？
- [ ] 反驳的理由是技术证据，不是情绪？

回应时：

- [ ] 没有感谢、夸奖、「你说得太对」式句子？
- [ ] 同意 = 陈述修复内容，不是表忠心？

**配合使用：** dev-review-code（评审意见怎么产出的，理解其分级与口径）、dev-verification（修完之后的验证纪律）
